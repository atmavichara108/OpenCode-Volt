## SERPlux release workflow distillation

### Decisions

- SERPlux execution workflow окончательно local-first: authoritative specs и
  весь workflow живут в `/home/rudra/Projects/serp/docs/specs/`; Vault specs
  SERPlux — archived/non-authoritative. Это approved exception к общей Vault
  policy.
- Единая входная команда — `/release v1.0.2: <свободное описание>`. Она
  включает intake, prompt-normalization/task-compilation, уточняющие вопросы,
  создание local spec и плана, approval gate, затем build/tests/reviewer/verifier
  и максимум 5 fix loops. `/prompt` остаётся optional diagnostic, `/spec` —
  read-only для existing specs.
- Основной release loop не выполняет автоматически `/dream`/flush, commit, tag,
  push или deploy. После verifier PASS — handoff пользователю:
  `READY_FOR_USER_INTEGRATION`/`AWAITING_USER_REVIEW`; `/commit`, push workflow,
  `/deploy` и отдельный ручной flush запускаются пользователем.
- Prompt-engineer реализован только как локальный SERPlux experiment внутри
  `plan`/`/release`; глобальный runtime prompt-engineer/task-compiler и
  automatic router не добавляются. Неизвестный маршрут — `UNROUTABLE`/`BLOCKED`.
- Две обязательные команды `/spec` + `/release` признаны лишним UX; генерация
  spec должна происходить внутри `/release`.

### Reusable pattern

- Для release-команд разделять intake/нормализацию, local spec/plan,
  explicit approval, build/test/review/verify и user handoff; не смешивать
  release loop с memory flush или публикацией результата.

### Lessons

- Наличие отдельной команды для обязательной генерации spec создаёт лишний
  переход и размывает единую точку входа; spec generation лучше делать частью
  утверждаемого release workflow.
- Commit-ограничения должны оставаться в собственных pre-commit/commit-guard
  проверках `/commit`, а не скрыто запускаться основным release loop.
