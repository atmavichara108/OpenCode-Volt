## SERPlux release workflow distillation

### Decisions

- SERPlux execution workflow окончательно local-first: authoritative specs и
  весь workflow живут в `/home/rudra/Projects/serp/docs/specs/`; Vault specs
  SERPlux — archived/non-authoritative. Это approved exception к общей Vault
  policy.
- Единая входная команда — `/release v1.0.2: <свободное описание>`. Она
  включает intake, prompt-normalization/task-compilation, уточняющие вопросы,
  создание local spec и плана, approval gate, затем build/tests/reviewer/verifier
  и максимум 5 fix loops. `/prompt` остаётся optional diagnostic, `/spec` —
  read-only для existing specs.
- Основной release loop не выполняет автоматически `/dream`/flush, commit, tag,
  push или deploy. После verifier PASS — handoff пользователю:
  `READY_FOR_USER_INTEGRATION`/`AWAITING_USER_REVIEW`; `/commit`, push workflow,
  `/deploy` и отдельный ручной flush запускаются пользователем.
- Prompt-engineer реализован только как локальный SERPlux experiment внутри
  `plan`/`/release`; глобальный runtime prompt-engineer/task-compiler и
  automatic router не добавляются. Неизвестный маршрут — `UNROUTABLE`/`BLOCKED`.
- Две обязательные команды `/spec` + `/release` признаны лишним UX; генерация
  spec должна происходить внутри `/release`.

### Reusable pattern

- Для release-команд разделять intake/нормализацию, local spec/plan,
  explicit approval, build/test/review/verify и user handoff; не смешивать
  release loop с memory flush или публикацией результата.

### Lessons

- Наличие отдельной команды для обязательной генерации spec создаёт лишний
  переход и размывает единую точку входа; spec generation лучше делать частью
  утверждаемого release workflow.
- Commit-ограничения должны оставаться в собственных pre-commit/commit-guard
  проверках `/commit`, а не скрыто запускаться основным release loop.

## Process overhead review: global HITL, /flush, /dream, risk-based spec

### Decisions

- Рассмотрена проблема overhead процесса в экосистеме. Вывод сессии:
  подтверждённой поломки нет — избыточность носит процессный характер,
  runtime-дефект не подтверждён.
- Зафиксированы причины избыточности процесса: тяжёлый pipeline для мелких
  задач, повторные чтения одних и тех же артефактов, empty meta handoff
  (пустые/малосодержательные передачи между агентами), reviewer max steps
  (достижение лимита шагов до завершения ревью), strict gates без
  масштабирования по risk.
- Создан/принят global human-in-the-loop (HITL) контракт:
  `~/.config/opencode/AGENTS.md` + ADR-009 (dotfiles/docs/decisions.md);
  clarification/plan/proposal до явного подтверждения пользователя,
  runtime-гейты `task: ask` и `edit: ask` в `opencode.jsonc`.
- Созданы/приняты команды `/flush` и `/dream` как управляемые точки
  дистилляции памяти.
- Verifier подтвердил acceptance PASS для HITL и `/flush` после reviewer
  evidence; live smoke выполняется в соседней сессии.
- Создан spec `06-Specs/Vault/risk-based-orchestration.md`, status:
  proposed. Реализация отложена до отдельной сессии.

### Reusable patterns

- Risk-based orchestration: объём процесса (pipeline, gates, verifier)
  масштабируется по risk/mutability задачи; lightweight docs-only route без
  verifier — валидный исход для low-risk изменений.
- HITL-контракт как общий паттерн: plan/proposal → явное user approval →
  исполнение только согласованного scope; изменение scope = новый proposal.
- Дистилляция памяти через `/dream`: append-only раздел session-log
  (Decisions / Reusable patterns / Lessons / Confirmed vs open / Next
  actionable focus) + минимальное обновление active-context без
  переписывания истории.

### Lessons

- Overhead ≠ поломка: сначала разбирать процессные причины (повторные
  чтения, empty handoff, несоразмерные гейты), потом думать о
  runtime-дефектах.
- Reviewer max steps и empty meta handoff — симптомы несоразмерности
  процесса, а не ошибки агентов; не фиксировать их как дефекты в facts.md.
