# Спец-отдел «Ротатор моделей»

Отдел Университета Агентских Систем, отвечающий за то, чтобы **агенты всегда
работали на живой модели** — без ручных переключений и без сюрпризов, когда
провайдер упал или кончилась квота.

## Мандат (слово владельца 2026-10-23, basis: quoted)
«у нас уже есть какое-то количество провайдеров, нам нужно настроить толково
ротатор моделей. для этого в УАС должен быть отдел который этим занимается».
«Толково» = не просто failover, а управляемое хозяйство: знать, что живо, что
кончилось, что кому отдавать, и почему переключились.

## Что значит «толково» — DoD отдела
1. **Один SSOT каталога.** `providers.json` ↔ `model-catalog.json` ↔ конфиг
   OpenCode не расходятся; скрипт сверки даёт отчёт расхождений (нет — значит
   ошибка).
2. **Живой health.** Probe по расписанию, телеметрия append-only; статус
   провайдера виден на любой момент без ручного запуска.
3. **Failover доказан.** Тест «выключили провайдера → агент переехал на живой →
   в журнале запись» проходит на живом прогоне, а не на словах.
4. **Роли учтены.** Модель подбирается по роли агента (coding/general/vision), а
   не «первая живая».
5. **Квоты не жгутся вслепую.** У каждого провайдера в каталоге — известные
   лимиты (RPM/RPD/месячные кредиты) и стоимость; ротатор не съедает дневной
   лимит за час.
6. **Приватность отмечена.** Для каждого провайдера отмечено, обучается ли он на
   наших данных (free-tier-риск), чтобы чувствительные задачи не улетали не туда.
7. **Журнал решений.** Каждое переключение — запись: кто, когда, почему (какая
   роль, какой сбой). Append-only, читаемо человеком.
8. **Связка с внешним миром.** Отчёт «какой провайдер лучше по роли» (median/p95)
   пригоден как публичный бенчмарк для писем вендорам (Q-002).

для роли до пересмотра.

## Формат журнала (контракт писателей, принят 2026-10-27)

Все писатели `control-plane/telemetry/provider-health.jsonl` — один файл, один
минимальный набор ключей: `ts`, `provider_id`, `status`, `models_count`,
`warnings`, `redacted: true` + **обязательная метка `source`** (кто пишет:
`probe`, `probe-rotator`, `rotate`…). Дополнительные поля (latency_ms,
usable_balance, key_source…) допустимы. Второго формата не создавать; панель
рубки читает только волт-путь (соглашение с ИЦ), state-кэш
`~/.local/state/opencode/rotator/` — только для отладки.

## Единый контракт классификации (зафиксирован УАС 2026-10-27)

Раскол порогов разрешён каноном (не голосованием): по рамке ХПФ «пороги, не
ярлыки» **отсутствие данных — это пустое поле, а не состояние».
Статус описывает доступность/качество ответа; баланс и латентность — отдельные
nullable-поля, никогда — часть статуса.

| Статус | Канон значения | Что делает ротация |
|---|---|---|
| `ACTIVE` | отвечает и моделей > 0 | здоров, не трогаем |
| `DEGRADED` | отвечает, но качество ниже порога (ошибка smoke, http 4xx, латентность сверх порога — при наличии замера) | здоров, не трогаем (проблема видна полями) |
| `BLOCKED` | моделей нет / 401 / 403 / пустой список | триггер ухода с текущего провайдера |
| `ERROR` | сеть / auth-store / 5xx | триггер ухода с текущего провайдера |
| `SKIPPED` | не наш контур / управляемый / backlog | не участвует в выборе |

Следствия для писателей:
- probe-rotator (проводник promo-provider-probe): «баланс неизвестен» —
  это `ACTIVE` с `usable_balance: null`, а не `DEGRADED`; `DEGRADED` — только
  упавший smoke/4xx/латентность сверх порога. Значения части старых строк
  сменятся при новом прогоне — ок, журнал append-only, «мигание» невозможно:
  порог один.
- probe.py: `latency_ms` — измеримое поле, не статус (как и было).
- Панель рубки показывает `status` + `source` + поля без переинтерпретации.
- Контракт живёт в этой карточке (канон-место); rotation.json ссылается на
  него в заметке формата.

## Границы
- УАС владеет каталогом и решениями; правку глобального `opencode.jsonc`

- Не трогает код приложений проектов.
- Секреты не появляются в файлах каталога, логах и отчётах.
