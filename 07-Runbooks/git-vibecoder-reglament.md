# Регламент работы с git: вайбкодер не трогает git руками

> Статус: обязателен для всех агентных сессий волта.
> Принцип: пользователь описывает желаемый результат словами —
> git-операции выполняют только агенты. Пользователь не вводит
> `checkout` / `add` / `commit` / `push` / `merge` / `stash` / `reset` /
> `revert` руками: цена ручной ошибки — потеря чужой параллельной работы.

## 1. Слова вместо команд

Пользователю достаточно сказать:

- «закоммить» — агент проверит scope, соберёт staged, проверит pre-commit,
  закоммитит в текущую ветку сессии;
- «запушь» — агент запушит текущую ветку (только fast-forward);
- «смержи в main» — только с явного разрешения (см. §4), агент сольёт
  и запушит;
- «откати» — агент сделает `revert` (безопасный), никогда `reset`;
- «что с гитом» — агент покажет ветку, статус и отставание от origin.

Никаких команд из этих слов пользователь не выполняет и не обязан знать.

## 2. Одна сессия — одна ветка

- Каждая агентная сессия работает в своей ветке `task/<slug>`.
- Коммит напрямую в `main` запрещён pre-commit хуком (кроме merge).
- Переключение веток — только через агента и только после проверки,
  что рабочее дерево не потеряет чужие изменения.
- Другая ветка — чужая территория: не коммитить туда, не откатывать,
  не переписывать историю.

## 3. Чужая работа неприкосновенна

- Незакоммиченные правки другого агента/сессии агент НЕ включает
  в свой коммит (селективный `add` только файлов своего scope).
- `stash` — только именованный (`stash push -m "..."`) и только
  с обязательным `pop` в конце операции; бесхозных stash не оставлять.
- Untracked-файлы чужого агента не удалять, не переносить, не коммитить.
- Перед `checkout`/`merge` агент проверяет `git status`: если переключение
  затёрло бы чужие изменения — STOP и доклад пользователю, а не `--force`.

## 4. Merge в main — только с разрешения

- Merge выполняется только после явного «смержи» / «разрешаю» от пользователя.
- Перед мержем: `fetch`, сверка с `origin/main`, pre-commit гейты,
  тесты затронутого контура (какие — по scope задачи).
- Push в `main` — только fast-forward. Force-push запрещён всегда
  и везде, без исключений.

## 5. Агентам запрещено

- `push --force` / `push -f` в любую ветку.
- `reset --hard`, `checkout -- <файл>`, `clean -fd` без явного разрешения
  на конкретный путь (это уничтожение работы).
- Коммит файлов вне своего scope («заодно»).
- Обход pre-commit (`--no-verify`) — если хук ругается, чинить причину.
- Додумывать разрешение: неоднозначное «ок»/«ага» — не разрешение на merge.

## 6. Отчёт агента после git-операции

Коротко, по-русски: ветка, что закоммичено/слито (хеш + одна строка),
куда запушено, что осталось незакоммиченным (и чьё оно, если известно).
Без листингов на экран — только итог.

## 7. Если что-то пошло не так

- Агент ничего не чинит «тихо»: останавливается и докладывает,
  что случилось и какие есть варианты.
- Откат опубликованного — только `revert` новым коммитом.
- Потерянное из дерева ищется в `stash list` и `reflog` до любых
  дальнейших действий.

## 8. Чужие репозитории агент доводит сам

- Если агент изменил файлы вне волта (dotfiles, конфиги, `~/.config`,
  `~/.local/share`), он сам коммитит и пушит их в том репозитории —
  на подходящей ветке, селективно, по тем же правилам (§2–§5).
- Пользователю не передаётся «зафиксируй сам» и не ставится задача
  идти в другой репозиторий объяснять происхождение правки.
  Кто сделал изменение — тот его и довёл до origin.
- Исключение: репозиторий с явным запретом от пользователя —
  тогда агент говорит это прямо и ждёт решения, а не молча бросает.

## 9. Кредо: кредиты — деньги, рутина — коду

- Оптимизация кредитов, эффективность и простота там, где уместно, —
  базовый принцип, а не опция. Процветание измеряется результатом
  на потраченный токен.
- Всё, что можно сделать программой (скрипт, команда, хук, плагин,
  скилл, cron/systemd), делается программой — а не повторной работой
  агентов за токены. Разовая настройка автоматизации всегда дешевле
  десяти ручных повторений.
- Перед вызовом субагента спрашивать: «это можно решить скриптом
  или готовой возможностью ноутбука?» Если да — писать код, не жечь
  контекст. Субагент — для суждений, а не для механики.
- Проверки evidence — дешёвыми командами (`grep`, `git diff --stat`,
  `pytest -q`), а не перечитыванием файлов целиком и не повторными
  ревизиями без новых оснований.
- Живые API-запросы — только по необходимости, минимальным профилем,
  со сверкой dry-run до и факта после. Бенчи и пробы не гоняются
  «на всякий случай».
- Зависимости рантайма (npm-пакеты провайдеров и т.п.) фиксируются
  письменно рядом с конфигом, который их требует: команда установки
  должна быть воспроизводима на чистой машине без телепатии.
  Пример: провайдер на `@ai-sdk/anthropic` невидим в списке моделей,
  пока пакет не установлен (`bun add @ai-sdk/anthropic` в каталоге
  конфига) — рестарт тут не помогает, и это должно быть записано,
  а не обнаружено заново.
