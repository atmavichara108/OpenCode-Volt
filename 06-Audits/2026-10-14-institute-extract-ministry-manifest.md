# Выжимка схемы манифеста ведомства

Самодостаточная выжимка схемы манифеста ведомства для будущей спеки УАС.
Первоисточник — артефакт `06-Audits/2026-10-14-institute-research-agent-sdk-landscape.md`
(386 строк, SDK-сверка). Читателю этого документа не нужно открывать первоисточник:
всё существенное для входа в спеку сведено здесь. Это выжимка, а не канонизация
и не внедрение.

---

## 1. Назначение и статус

- **Что это.** Проект схемы манифеста ведомства (`ministry-manifest`) — машиночитаемое
  описание одного ведомства сети Корабля: кто это, какая компетенция, через какие
  сессии живёт, откуда мандат, куда сдаёт отчёты и куда ему пишут, где его спеки,
  какие границы и какой порт в Центральный Узел.
- **Статус: проект для спеки, не внедрение.** Документ — шаг «SDK-сверка» из цепочки
  Р-006: SDK-сверка → проект `ministry-manifest.yaml` → УАС-спека на двух основаниях →
  спека Лабы. Сам манифест не пишется и не разворачивается здесь.
- **Слой размещения.** `docs/org/` в волте (решение Rudra 2026-10-14, Р-005: вариант B
  усиленный — «тихая папка + сильная юрисдикция УАС»; вариант `00-Org/` отвергнут;
  вариант C «полная укладка» отклонён). Принят **гибрид A+B** из исследования ЦУ/УАС:
  слой манифестов/контрактов в волте + документы real estate per-repo.
- **Какие решения уже приняты** (из `01-Policies/decisions-registry.md`):
  - Р-004 — создано ведомство УАС: юрисдикция над агентской инфраструктурой, включая
    стандарты манифестов и реестры агентов/скиллов/команд.
  - Р-005 — слой манифестов ведомств: `docs/org/` в волте.
  - Р-006 — порядок: SDK-сверка → проект схемы → УАС-спека → спека Лабы.
  - Р-009 — семантика мандатов: апрув в корне канала (слово Rudra), сосед не может
    изготовить мандат, provenance обязателен.
- **Какие решения ждут.** Старт УАС-спеки (готовность: да, блокеров нет — по слову
  Rudra); детали схемы, перечисленные в разделе «Открытые вопросы» ниже.

## 2. Обоснование (одна страница)

**Зачем манифест вообще нужен.** Сегодня ведомство фактически равно сессии, а швы
между ведомствами не оформлены явными сущностями («провода торчат наружу»). Манифест —
это прокладка между сущностью (сессией-носителем) и её зонами/портом: одно ведомство
= один читаемый структурный файл, по которому видно, что это за место, чем оно
занимается и как с ним связаться, без чтения всей памяти и всех спек.

**Внешнее подтверждение.** Сверка SDK-ландшафта 2026-10-14 подтвердила: манифест
ведомства ≈ AgentCard из A2A (идентичность + способности + скиллы + адреса) и
совпадает с паттерном «реестр как код» (registry-as-code) — агенты/локации объявляются
версионируемыми файлами в git, а не в runtime-БД. Наш выбор «машиночитаемый файл в git»
совпадает с индустриальным трендом сходимости (A2A, MCP, реестры).

**Главное отличие от внешних стандартов — обязательное происхождение мандата.**
Внешняя AgentCard лишь заявляет способности; вопрос «по какому праву этот агент
существует и действует» там не ставится. У нас мандат не самозванный: поле
`mandate-source` (источник полномочия) — **обязательное**, а не опциональное. Это наше
дополнение поверх AgentCard, у которой такого поля нет. Его подкрепляет Р-009: сосед
не может изготовить мандат, provenance обязателен.

**Что сознательно НЕ берём из внешних стандартов (и почему):**

- **Полный механизм обнаружения (A2A discovery: well-known URI + каталоги + подпись
  карточки + кэширование).** Не берём целиком: мы одна локальная экосистема на одном
  хосте, а не кросс-вендорная сеть. Достаточно registry-as-code (у нас уже есть
  `claims.jsonl` и реестр отсеков); нужен лишь лёгкий каталог ведомств «все манифесты
  одним списком».
- **Полноценный типизированный жизненный цикл задачи (A2A Task, 7 состояний +
  подписки + cancel).** Избыточен для наших писем: у нас уже есть квитанции
  (started / finished / cannot). Если типизировать — только три состояния плюс id
  задачи, без push-подписок и отмены.
- **Полные wire-привязки (JSON-RPC/gRPC/HTTP) и строгий opaque execution.** Наша
  координация — письма между равными персистентными сессиями, а не вызов инструмента
  серверу; письмо осознанно переносит контекст.

**Что подтверждает наш гибрид A+B.** Разделение гейтов «качество отдельно от приёмки»
(reviewer → verifier) подтверждается guardrails/evaluation; тройное разделение памяти
session-log / active-context / facts — буквально Session / State / Memory из ADK;
перенаправление чужого интента — handoffs/agent routing. Наша форма «персистентная
именованная сессия-место» (В2) — осознанное отклонение от эфемерных внешних
субагентов, обоснованное каноном (сессии-места, `048`) и С3-становлением, а не
внешней инженерией.

## 3. Схема: перечень полей

Поля как человеческое описание (не файл конфигурации). Обязательность — черновик
для спеки УАС; примеры значений — ориентировочные.

### Обязательные поля

| Поле | Что означает | Зачем нужно | Пример значения |
|---|---|---|---|
| `id` (идентификатор) | устойчивый короткий slug латиницей, аналог имени файла агента | по нему адресуются письма и строки реестра | `institute-adv-tech` |
| `name` / `shadow` (имя и тень) | рабочее имя для адресации и «тень» (persona/роль по закону тени) | имя — для адресации, тень — для диалога; разделяются осознанно | имя «Институт Передовых Технологий», тень «носитель исследования» |
| `jurisdiction` (юрисдикция/компетенция) | что входит в ведомство, что перенаправляется | граница ответственности; источник — карта компетенций контракта сети | «исследования передовых технологий; чужую компетенцию не исследует» |
| `carrier-sessions` (сессии-носители) | какие реальные сессии OpenCode являются этим ведомством | привязка манифеста к живой сущности (сессии/роли) | роль `institute-adv-tech` из `claims.jsonl` |
| `mandate-source` (источник мандата/провенанс) | откуда взяты компетенция и полномочие (ссылка на решение/спек-контракт) | чтобы мандат не был самозванным (обязательное отличие от AgentCard) | `ship-research-network` §3 + слово Rudra |
| `report-address` (адрес приёма отчётов) | куда ведомство сдаёт отчёты | каноническая точка приёма — Центральный Узел | сессия-носитель ЦУ `ses_ecae229fcffef5FrLdWOJLos1K` |
| `peer-address` (адрес общего канала) | как доставить письмо ведомству (сессия/роль для `find --role`) | адрес peer-comms; аналог endpoint в AgentCard | роль `institute-adv-tech` через `find --role` |
| `spec-home` (домен спек) | где лежат спеки этого ведомства | `<repo>/docs/specs/`; источник правды по спекам | `OpenCode-Vault/docs/specs/` |
| `status` (статус) | состояние ведомства + дата | аналог статуса карточки проекта | `active, 2026-10-14` |
| `boundaries` / `limits` (границы и лимиты) | что ведомство не делает + количественные потолки | аналог caps (глубина, параллельность) Claude SDK | «не правит код приложений; ≤3 активных отсека» |
| `ports` (порт ЦУ) | точки входа, через которые ведомство принимает/отдаёт интенты ЦУ | центральный вход координатора без размножения primary | ЦУ-порт приёма внешних кейсов |

> **Требование раздельных полей адреса.** Адрес приёма отчётов и адрес общего канала —
> два разных поля, не одно. Это записано как вход в спеку УАС (предложение Института,
> `06-Audits/2026-10-13-ship-research-registry.md`, раздел «Каноническая адресация»):
> ведомство может отчитываться в одну точку (ЦУ), а письма принимать по своему
> peer-адресу. В черновике SDK-сверки эти два смысла были слиты в одном `peer-address`.

### Опциональные поля

| Поле | Что означает | Зачем нужно | Пример значения |
|---|---|---|---|
| `capabilities` / `skills` | заявленные способности и скиллы (id/name/description/tags/examples) | аналог AgentSkill | скилл `capability-routing` |
| `memory-zones` | зоны памяти, которыми владеет ведомство (по реестру отсеков) | один отсек = одна тема = одна файловая зона | отсек «исследования Института» |
| `file-zones` | файловые зоны записи (что ведомство вправе править) | граница записи на диск | `06-Audits/` (свои артефакты) |
| `evidence-policy` | политика доказательств: какой verifier/reviewer, критерий приёмки | что считается evidence | verifier acceptance + commit/tag |

## 4. Разбор спорных / неочевидных полей

- **`mandate-source` (источник мандата).** Фиксирует, кто и когда дал основание
  ведомству (цитата/ссылка на слово Rudra или спек-контракт). «Мандат не самозванный»
  значит: полномочие прослеживается до решения Rudra, а не декларируется самим
  ведомством; сосед не может изготовить мандат (Р-009). Это единственное поле, по
  которому наша схема жёстче внешних карточек.
- **`carrier-sessions` (сессии-носители).** Сегодня ведомство = сессия (явная
  сущность). Поле — шов к будущему: оно привязывает манифест к конкретной сессии/роли
  сейчас, но завтра ведомство может стать самостоятельной явной сущностью (путь
  С3-становления), и тогда поле указывает на новую сущность, не ломая схему.
- **`boundaries` / `limits` (границы и лимиты).** Перекликается с ограничением
  активных отсеков из реестра: пересечение зон активных отсеков запрещено, ≤3 активных.
  Манифест ссылается на отсеки реестра, а не плодит новые; лимиты — количественные
  потолки (аналог caps spawn-depth / concurrent из Claude SDK).
- **`ports` (порт ЦУ).** Центральный вход координатора реализуется как В1-порт
  («одежда-персона»), который подключается к каждому ведомству **без размножения
  основного агента ведомства**: ведомство остаётся сессией-носителем, порт — прокладка,
  а не ещё один голос. Завтра порт может сам стать сущностью (С3-становление), но
  сегодня это манифест-объект, а не отдельный primary.

## 6. Открытые вопросы

### Для ЦУ / Rudra (решения до внедрения)

1. **Точная раскладка каталога.** Р-005 зафиксировал слой `docs/org/` и отверг
   `00-Org/`, но внутренняя структура не зафиксирована: подкаталог манифестов,
   имя файла (`ministry-manifest.yaml`), конвенция имён по ведомствам.
2. **Владелец реестра манифестов.** УАС имеет юрисдикцию над «реестрами
   агентов/скиллов/команд» и «стандартами манифестов» (Р-004), но конкретный
   владелец реестра манифестов (кто ведёт каталог всех манифестов) не назначен.
3. **Старые адреса в реестре сети.** Канон объявил прежние адреса историческими
   (напр. «Централизация» `ses_eceb23a71ffeJO9QnFou8VngZC`), но что делать с ними при
   переходе на манифесты — переписать, пометить, оставить — не решено.
4. **Обязательность манифеста.** Обязателен ли манифест для каждого нового ведомства
   (условие создания) или доброволен — не решено.
5. **Соотношение с реестром отсеков.** Принцип задан (манифест ссылается на отсеки
   реестра, не плодит новые), но точная механика ссылки и владелец реестра отсеков
   в мастерской — не решены.

### Для спеки УАС (детали схемы)

6. **Лёгкий discovery.** Нужен ли единый каталог ведомств («все манифесты одним
   списком») как registry-as-code поверх `claims.jsonl` и реестра отсеков — и где он
   живёт.
7. **Typed task lifecycle.** Брать ли типизацию состояний задачи (только три состояния
   + id, без push/cancel) или оставить receipt-квитанции как есть.
