## 1. Инвентаризация: что реально в стеке пип-боя (мои чтения кода)

Сверка со спекой §3.1 — все заявленные размеры подтверждены построчно:
actions.py 1111, App.js 734, model-router.py 599, v8bis.html 593,
observer.py 564, Workspace.js 506, pipboy.py 496, termproxy.py 469.
Модулей ровно 18 (Acceptance…Upgrade, 45–286 строк каждый).

### 1.1. Бэкенд — чистый stdlib, ноль зависимостей (подтверждено импортами)

pipboy.py: http.server (SimpleHTTPRequestHandler + ThreadingHTTPServer),
threading, subprocess, argparse, json, pathlib. Никаких Flask/FastAPI/
aiohttp/websockets — импортов внешних пакетов нет ни в одном из пяти
Python-файлов. observer.py — hashlib/re/json/subprocess (read-only CLI).
model-router.py — fcntl (flock), difflib. termproxy.py — socket + hashlib:
WebSocket-хендшейк написан руками (sha1+base64, raw socket, HTTP и WS на
одном порту по первому байту).

SSE (pipboy.py:55-175): file-watcher раз в 2 с считает sha256-дайджест
входов (registry.json + generated/snapshot.json), изменение инкрементит
seq; GET /event отдаёт text/event-stream с heartbeat; reconnect и
Last-Event-ID берёт на себя браузер (EventSource).

/action (pipboy.py:181-197): GET + whitelist ALLOWED (~19-21 операций),
исполнение в actions.py. Мутации через GET при декларации read-only —
контрактный дизонанс подтверждён кодом (не гипотеза).

### 1.2. Фронтенд — ванильные ES-модули, без сборки (подтверждено)

Ни package.json, ни node_modules, ни конфигов сборки в репо нет. Ядро:
EventBus.js — 22 строки (Map event -> Set<fn>, emit с изоляцией ошибок);
Module.js — 79 строк (жизненный цикл mount/refresh/unmount, esc/linkify,
fetchJson, action через GET); Workspace.js — 506 строк (PROFILES
Overview/Build/Control/Models/Capture/All, keep-alive, persistence);
App.js — 734 строки (APP_VERSION v11.1, цепочка registerModule из 18
модулей, командная палитра, хоткеи Alt+Shift).

Тест: app/core/Workspace.test.mjs — нативный node:test + node:assert
(109 строк, без единого пакета). Это редкость: ядро покрыто тестом,
который запускается голой нодой.

Кувалда подтверждена кодом: App.js:545 `new EventSource("/event")`,
App.js:553 — на любой digest вызывает refreshAll() всех модулей.

xterm vendor: 5.5.0 (289 КБ) + fit-аддон (свой, 1.8 КБ). Актуальная линия
2026 — @xterm/xterm 6.0.0 (npm): vendored версия отстаёт на одну мажорную.
Тема «xterm vendor — проверить свежесть» из §3.1 закрыта: устарел.

### 1.3. Кривое, подтверждённое кодом (чиним в Ship)

- Три слоя прототипов v4-v7 в одном коде; входной зоопарк
  index.html (12 строк) -> index-v10.html (658) -> App.js v11.1.
- App.js — god-модуль на входе: статические импорты всех 18 модулей
  в одном файле (строки 13-32).
- actions.py — плоский список do_* на 1111 строк: workspace/capture/link/
  ecosystem/models в одном файле, без доменной структуры.
- Мутации через GET (см. 1.1); refreshAll-кувалда (см. 1.2);
  дублирование readiness бэк/фронт; data.json-зомби (60 КБ) лежит рядом
  с registry.json (62 КБ) — дублирование формы подтверждено весом файлов.
- env-наследование spawn-процессов (actions.py:927-937) — путь утечки
  секретов, отмечен спекой; при переносе — чистый env whitelist.

### 1.4. Что это значит для вопроса стека

Стек пип-боя — это уже осознанный выбор «ваниль + stdlib», и он
не мёртвый угол, а мейнстрим-тренд 2026 (см. раздел 6). Наследие
переносится: ядро 607 строк (EventBus+Module+Workspace) + тест,
паттерн snapshot, whitelist-действия. Цена вопроса — не «какой фреймворк
выбрать», а «хватает ли ванили для POST-гейтов, форм и точечных
обновлений, или добавить минимальную библиотеку».

## 2. Варианты стека (четыре, честное сравнение)

### В1. Ванильный JS + Python 3 stdlib-only (рекомендация Apps-dev)

Фронт: ES-модули без фреймворков и без сборки; ядро EventBus/Module/
Workspace переносится. Бэк: stdlib (http.server, threading, subprocess,
fcntl, socket — как pipboy.py/observer.py/termproxy.py).

Проверка на прочность — где В1 болит:

1. Реактивность ручная. refreshAll-кувалду чинят руками: подписка модулей
   на типы digest (server-state.catalog vs server-state.registry) — это
   +50-80 строк в ядре, но без библиотеки мелкозернистых сигналов
   обновления пишутся каждым модулем.
2. POST-транспорт и формы. fetch POST + CSRF-токен + owner-gate-прослойка
   пишутся руками (порядка 60-100 строк в ядре Ship). htmx даёт hx-post
   из коробки — у В1 это ручная работа.
3. http.server официально «not recommended for production» (офдоки,
   обновлено 2026-11-03). Для нашего контура (127.0.0.1, один юзер,
   read-only + whitelist) риск приемлем — это та же база, на которой
   пип-бой уже живёт.
4. Скорость dev-цикла максимальная из всех вариантов: ноль сборки,
   ноль npm, ноль Type-инфраструктуры; правка = save + reload.

Итог В1: держит 5 из 6 критериев; слабое место — ручной код реактивности
и форм (оцениваю +150-200 строк в ядре однократно).

### В2. Ваниль + минимальный бор-набор (htmx-класс / Alpine-класс)

Сравниваю именно read-only/скорость/читаемость, состояние на 2026-11-03:

- htmx: 2.0.10 (21.04.2026) — npm latest; 4.0.0 (28.08.2026) — fetch-based,
  hx-sse/hx-ws/core-extensions, Idiomorph-морфинг; 4.0 станет latest
  только в начале 2027. ~48k звёзд; «most admired frontend tool»
  (State of JS 2024, публикация фев 2026); ~14 КБ.
- Alpine.js: v3.17.x (обновления 2026 активны; 3.15.8 — фев 2026),
  ~7 КБ gzipped, 226 035 живых доменов (краул окт 2026), поддерживается
  автором; декларативная реактивность в HTML-атрибутах.
- Совместное употребление — норма 2026: Alpine стоит на 26.55% доменов
  htmx (краул-данные окт 2026).

Плюсы против В1: POST/формы/SSE-свойства из коробки (hx-post, hx-sse);
меньше ручного кода интерактива; кейсы 2025-2026 фиксируют минус 67%
кода при переводе админ-дашбордов с React (и до 90% LOC в других кейсах).

Минусы против В1 — решающие: парадигма «сервер рендерит HTML-фрагменты»
противоречит текущему контракту «JSON/snapshot -> клиент рендерит».
Все 18 модулей и ядро Workspace переписываются, а не переносятся
(критерий 6 наследия провален). HTML появляется в Python-строках —
для владельца-не-разработчика читаемость двухдоменного рендера ниже,
чем у готовых ES-модулей с русскими докстрингами. Состояние распадается
на два места (DOM + сервер) — то, от чего канон «файлы — истина»
предостерегает.

### В3. Компонентный фронт с сборкой (Lit 5 КБ / Preact 3 КБ + Signals)

Состояние 2026: Lit — OpenJS Foundation, ~5 КБ, web components, жив;
Preact — ~3 КБ + Signals (мелкозернистые обновления, до 3x на
реактивных сценариях), жив. Оба — «легально» для дашборда.

Плюсы: лучший runtime-UX при частых точечных обновлениях (Signals чинит
именно «кувалду»); компонентная изоляция; тест-экосистема богаче.

Минусы — решающие для владельца-не-разработчика: появляется сборка
(npm, бандлер, dev-сервер — тот самый churn webpack->Vite->Turbopack,
который отрасль 2026 называет скрытой стоимостью); State of JS 2025:
медиана разработчиков компилирует 100% браузерного кода — наш путь
осознанно другой, и он дешевле в поддержке; компонентная модель —
новый язык для владельца (lit/reactive-контракты, JSX/шаблоны);
наследие переносится частично (Workspace/профили да, модули — нет);
зависимость от чужого release-цикла в коде, который правит владелец.
Отклоняю: ценник сборки против канона «исправлять пип-бой, а не
менять стек» не окупается — наш UI это тайлы и формы, а не сложная
SPA-состояниевая поверхность.

### В4. TUI-путь: Textual (Python, режим textual serve)

Состояние 2026: жив и активен; `textual serve` встроен в фреймворк
(textual-serve 1.1.3, PyPI; веб через websocket-протокол), textual-web —
публикация наружу. Python-API один — терминал и браузер.

Плюсы: весь код на Python (один язык для владельца); виджеты/скроллбары
из коробки; хорошие формы.

Минусы: дублирует opencode TUI (рубка станет вторым терминальным
прибором, а веб-рубка — тем же терминалом в браузере); стиль
crypto-cyber-solarpunk уже реализован в вебе темами Phosphor/Amber/Ice,
в Textual его надо делать заново; v8bis-референс «задача в центре» и
v11-профили не переносятся; тайлы/окна/граф связей — не его модель;
websocket-протокол textual-serve — чужая прослойка между бэком и UI.
Отклоняю для рубки; пригоден для утилит Лабы.

### 2.5. Сравнительная таблица по шести критериям

Веса по убыванию (бриф): 1 качество, 2 скорость, 3 модульность,
4 читаемость владельцем, 5 зрелость экосистемы под наши задачи,
6 совместимость с наследием. Шкала 1-5, 5 — лучше.

| Критерий (вес) | В1 ваниль+stdlib | В2 +htmx/Alpine | В3 Lit/Preact+сборка | В4 Textual |
|---|---|---|---|---|
| 1. Качество/надёжность | 4 (ручной код реактивности — риск ошибок, но ядро тестируемо) | 4 (библиотеки стабильны: htmx 1838+ тестов) | 5 (Signals/компоненты зрелы) | 4 (зрелый фреймворк) |
| 2a. Скорость runtime | 4 (ноль оверхеда; обновления руками) | 4 (морфинг DOM в 4.0) | 5 (Signals: точечные без VDOM) | 3 (веб через websocket-прослойку) |
| 2b. Скорость dev-цикла | 5 (save+reload, ноль сборки) | 5 (тот же ноль сборки) | 2 (npm/бандл/dev-сервер) | 4 (Python-цикл быстр) |
| 3. Модульность | 4 (ES-модули; god-App.js режем) | 3 (фрагменты сервера — резка менее естественна) | 5 (компоненты) | 4 (виджеты/экраны) |

требование канона к коду мкода) В1 выигрывает с отрывом, критерий 6 —
решающий вес канона Р-074 (наследие переносится, не переписывается).

## 3. Вердикт ИПТ

База Ship — В1: ванильный JS (ES-модули, без фреймворков, без сборки) +
Python 3 stdlib-only. Рекомендация Apps-dev проверку на прочность
выдержала: по шести критериям В1 выигрывает или делит первое место;
единственные реальные слабости (ручная реактивность, ручной POST-слой)
закрываются разовой достройкой ядра, а не сменой стека.

Три точечных усиления (паттерны из В2 — без зависимостей):
1. POST-транспорт /api/op в стиле htmx hx-post: fetch POST + CSRF-токен
   + обязательная прослойка Ворота (owner-gate) на send-класс операций.
   Пишется один раз в ядре Ship (60-100 строк), потом это «паттерн
   всего стека» как whitelist /action сейчас.
2. Инвалидация по типам digest вместо refreshAll-кувалды: SSE-событие
   несёт класс изменения (registry/sessions/mail/incidents), модуль
   подписан на свои классы. +50-80 строк в EventBus-ядре.
3. Обновление xterm vendor 5.5.0 -> @xterm/xterm 6.0.0 при переносе
   терминала (волна B; на волну A не влияет).

Уровень языка: высокоуровневый по обе стороны (JS для UI, Python для
бэка) — единственный вариант, где владелец может читать и править
обе половины без чужих абстракций. Стиль: продолжение существующего
(ES-модули с докстрингами, stdlib-CLI с argparse), а не новая мода.
Сборка: не вводим; тест-раннер — нативный node:test (уже в репо).

## 4. Непреложное наследие (берём в ЛЮБОМ варианте)

Из инвентаризации (спека §3.1 + мои чтения раздела 1):

Код и паттерны:
1. Ядро app/core: EventBus (22 строки) + Module (79) + Workspace (506)
   + тест node:test — перенос почти как есть (стек совпадает, §3.1.E).
2. SSE-транспорт /event: text/event-stream, digest->seq, heartbeat,
   reconnect силами браузера — паттерн живости сохраняем и развиваем
   (типизированные digest, усиление 2 из вердикта).
3. Whitelist действий (ALLOWED в pipboy.py) — образец безопасного
   обратного канала; в Ship эволюционирует в POST /api/op + Ворота.
4. observer-контракт «markdown -> snapshot -> UI»: файлы — истина,

5. pipboy.py-хост: 127.0.0.1, read-only GET/HEAD, авто-гашение простоя,
   pid/log во временной директории — адаптируем (мал и чист, §3.1.E).
6. model-router.py: flock, бэкап, отмена тостом — канон ротатора.
7. xterm vendor + свой fit-аддон: терминал в браузере без внешних
   зависимостей (обновить версию — см. вердикт).
8. Темы Phosphor/Amber/Ice (rgba-переменные) и профили Workspace —
   стиль уже наш, переписывать некуда.

Данные и каноны:
9. registry.json — источник правды слоя PLAN; snapshot.json (схема 1.1).
10. control-plane: model-catalog (ротатор), инциденты/audit-log.
11. ship-mail ящики (Р-028) — Global Inbox читает файлы напрямую.
12. Профили контекстов Overview/Build/Control/Models/Capture/All.
13. «Задача в центре» (v8-BIS) и живой рассказчик — концепты волн.

Хороним (не переносим): слой v4-v7, data.json (зомби), GET-мутации,
монолит actions.py как единый файл, дублирование readiness,
meta.projections мёртвую, простыню status_note.

## 5. Контракты стыковки Ship с mcode

Граница 03.11 (канон): пип-бой (и Ship как его наследник) без
зависимостей с mcode. Это значит: Ship не импортирует код mcode,
не читает его внутренние хранилища и не запускается от его процессов.
Стыковка — только через контракты данных и публичный API opencode.

Ship наследует (как пип-бой):
1. Управление сессиями через `opencode serve` (публичный API):
   сессии/статусы/сообщения/реакции; замеры Лабы (runset-1, 27.10.2026):
   /api/session 15.2 мс медиана (24.7 КБ), active 7.4 мс; НЕ поллить
   тяжёлое (session/stats 3.4 с медиана) и полный список (1.0 МБ) —
   кэш/delta. Serve-эндпоинт — единственная рантайм-зависимость.
2. Файловые контракты волта: registry.json, snapshot.json, TASKS.md,
   decision-queue, idea-graph, ship-mail ящики — read-only свободно.
3. Control-plane каноны: ротатор читает ТОЛЬКО волт-канон, инциденты —
   живой источник; push-канон как в пип-бое.

Ship НЕ наследует от mcode:
- data.json и слой v4-v7 (зомби и прототипы);
- /tmp/mcode pid/state-файлы пип-боя (у Ship свои tmp-пути);
- GET-мутации и actions.py-монолит (режутся на домены при переносе);
- наследование env-полностью в spawn (чистый env whitelist — урок
  actions.py:927-937).

Контракт POST-транспорта (главная стыковка волны A):
- Ship: POST /api/op {op, params, actor, csrf} — исполнение только
  после подтверждения Ворота (owner-gate форма) для send-класса
  (письмо, апрув, старт квеста); журнал акторов.
- mcode: владелец пишет код по спеке отсека; Ship пишет в систему
  только через Рубка-контроллер (один писатель, ИЦ-паттерн).
- dunst: отдельный канал бэка (subprocess notify-send), НЕ через SSE —
  не смешивать (спека §3.1.F, пункт 5).

## 6. Риски по вариантам + живые источники

### 6.1. Риски

В1 (база):
- http.server официально не для продакшена (офдоки Python 3.15.2,
  обновлены 2026-11-03): symlink-follow и только базовые проверки.
  Митигация уже в наследии: привязка 127.0.0.1, read-only, whitelist,
  один пользователь. Риск: низкий.
- Ручная реактивность растёт линейно с числом модулей. Митигация:
  достройка ядра (типизированные digest + подписки) на волне A,
  до первой партии новых модулей. Риск: средний, управляемый.
- Единственный тест на ядро. Митигация: при переносе добрать тесты
  на EventBus/подписки digest и POST-слой (node:test, без пакетов).
- Осознанное меньшинство: медиана разработчиков 2025-2026 компилирует
  весь код (State of JS 2025) — риск «выпасть из мейнстрима» принят
  каноном; тренд no-build в 2026 усиливается (см. источники).

В2 (+htmx/Alpine): парадигмальный разрыв с наследием (переписать 18
модулей); двойное место рендера (HTML в Python-строках) — читаемость
для владельца ниже; htmx 4.0 не latest до начала 2027 — брать 2.x,
но это ещё один транзит впереди. Риск: высокий для критерия 6.

В3 (Lit/Preact+сборка): сборка/npm в коде, который правит не-разработчик
(churn тулчейна — документированная стоимость 2026); чужой release-цикл
в зависимостях; 100%-компиляторная культура против канона читаемости.
Риск: высокий для критериев 4 и 6.

В4 (Textual): дублирование opencode TUI; websocket-прослойка
textual-serve между бэком и UI (чужой протокол в нашем контуре);
стиль/тайлы/граф — не его модель; v8bis-референс теряется.
Риск: средний, но ценность ниже всех.

AndroidOS-родство (Пип-Бой на Android, Р-074): выигрывает В1/В2 —
чистый веб без сборки ставится как PWA на домашний экран (Chrome
Android) или в киоск-обёртку (Webview Kiosk — опенсорс, обновлён
2026-10-28); SSE (EventSource) и WebSocket в Chrome/WebView работают.
Сервер остаётся на хосте (или Termux) — Android только экран.
Для В3 — тот же веб, но через сборку; для В4 — textual-web beta,
киоск-стабильность под вопросом.
