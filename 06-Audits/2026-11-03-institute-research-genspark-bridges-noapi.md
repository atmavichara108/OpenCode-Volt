# Мосты к SaaS без публичного API: кейс Genspark

## 0. Провена (дословно)

Слово владельца 2026-11-01 (basis: quoted, через Maya, реестр Р-068):
«в генспарке у меня есть почти безлимитный доступ к последним моделям в ai chat...
прямого апи нет, нужно придумать как это сделать».

Слово владельца 2026-11-03 (basis: quoted, Р-072, из капитанского портала):
«Да на все рекомендации. А генспарк булем зондировать с другого акка, не с моей
платной подписки чтобы не рисковать».

Мандаты ЦУ: `ipt-genspark-research` (исследование мостов и TOS) +
`genspark-ipt-frame` (уточнение рамок). Каноны:

- **Р-068** (2026-11-01): два моста — Genmail (рутина) и Genspark (модели);
  Genspark = только зонды до подтверждения владельцем риска аккаунта; в ротацию —
  после устойчивых зондов + слова; секреты — Ворота, вне репо; ведомства:
  ИПТ (паттерны без-API + TOS-чек), Ротатор (ротация), ИС/Лаба (инкубация шлюза).
- **Р-072** (2026-11-03): зонды Genspark — только с отдельного аккаунта; аккаунт
  владельца с платной подпиской исключён из любой автоматизации; ротация — только
  отдельным словом владельца; доступы/секреты — через Ворота; без пошаговой
  валидации аккаунта (существование → активность → лимиты) — не зондировать;
  создание стороннего аккаунта — только слово владельца.

Исходный факт базы УАС (не верифицировался заново — принят как исходная точка):
в `control-plane/telemetry/provider-health.jsonl` Genspark — строка-заглушка
`source=frame`, warnings `frame_R-068, out_of_catalog, probe_mode_only,
no_direct_api`; «вне каталога, режим зондов — не провайдер ротации».

## 2. Карта паттернов моста к SaaS без API

Паттерны по мандату: (а) эмуляция клиента, (б) профильный headless,
(в) локальный шлюз с OpenAI-совместимым фасадом. Реальность проекта deanxv
показывает: устойчивые мосты — это (в) с вкраплениями (б) (headless только там,
где без него не пройти капчу) — не «либо-либо».

### 2.1 Паттерн (а): эмуляция клиента (HTTP-сессия с cookie веба)

**Как устроен.** Один раз человек логинится в браузере; из F12/DOM экспортируется
`session_id`-cookie (для Genspark он один достаточен). Далее мост говорит с
веб-эндпоинтом напрямую по HTTP: браузерные заголовки (UA обязателен — без него
Genspark отдаёт 400 «bad request cf», что выглядит как CF-блок, но это
прикладная проверка), TLS-отпечаток браузера — через curl_cffi (impersonate),
иначе Cloudflare режет на TLS-фингерпринте. Ответы приходят SSE-потоком — мост
пересобирает их в OpenAI-формат.

**Живые примеры (GitHub, поиск 2026-11-03, всего по «genspark» 1361 репо):**
`xinxinshuhao-create/genspark2api` (28★, мост = чистый HTTP, браузер один раз),
`SharpWizard/genspark-py` (9★, неофициальный клиент: B2C-логин + стрим-чат,
TLS-имперсонация curl_cffi), `nishlumi/genspark-api-client` (5★, JS-библиотека),
`joysey/genspark-to-obsidian` (5★, экспорт диалогов), `cccnam5158/sync-multi-chat`
(16★, браузерная синхронизация промпта в подписные веб-чаты — вариант «скрипт
в странице» без выноса за браузер).

**Хрупкость (а):** cookie живёт ~20 дней (session_id), вспомогательные auth-токены
~24 ч (автопродлеваются), anti-bot cookie ~30 мин (обновляется на каждый запрос)
— по замерам xinxinshuhao 09-2026; ре-логин автоматический, без капчи.
Ломается при: смене формы веб-эндпоинта (поля/URL `ask`-запроса), ужесточении
TLS/CF-фингерпринта, принудительном reCAPTCHA v3 на чат-путь (см. deanxv),
смене схемы моделей/сессий. Средняя цена поддержки по чужим репо: точечные
фиксы 1–2 раза в месяц (issue-поток deanxv), т.е. ~2–6 ч/мес на следящий.

**Требования к среде (а):** один экспорт cookie из браузера (вручную), egress
желательно отдельный на аккаунт, TLS-имперсонация (curl_cffi), иначе прокси-пул.

### 2.2 Паттерн (б): профильный headless (управляемый браузер)

**Как устроен.** Playwright/Puppeteer держит настоящий браузер (профиль с
логином) и делает то же, что человек: открыл чат, послал промпт, забрал ответ.
Браузер может жить в контуре постоянно (long-lived сессия) или подниматься
эпизодически (логин, капча, экспорт cookie) — второй вариант дешевле и его и
используют мосты как вспомогательный.

**Живые примеры:** `deanxv/genspark-playwright-proxy` (7022-порт, docker; сервис
проходит reCAPTCHA v3 и отдаёт токен мосту; рекомендован резидентный прокси —
«после прокси вероятность прохождения выше»), `Jun-Murakami/AI-Browser` (51★,
десктоп-клиент-обёртка над веб-чартами ChatGPT/Gemini/Claude/…/Genspark),
`stolot0mt0m/claude-chromium-native-messaging` (83★, подводка расширения Claude
в Chrome к альтернативным Chromium-браузерам — тот же класс задач для другого
SaaS).

**Хрупкость (б):** самая высокая цена среды (браузер + профиль + память), но
именно он пробивает капчи, которые убивают (а). Ломается при: изменении DOM
(селекторы), анти-автоматизации Playwright-отпечатка (CDP-детект), усложнении
капчи. reCAPTCHA v3 — скоринговая: плохой IP/отпечаток = низкий скор = «понижение
интеллекта» или блок пути (по deanxv — официальное принуждение к v3, 2026).

**Требования к среде (б):** docker с браузером, резидентный egress-прокси
(рекомендация автора), ~0.5–1 ГБ RAM на сессию; сопровождение селекторов.

### 2.3 Паттерн (в): локальный шлюз с OpenAI-совместимым фасадом

**Как устроен.** Локальный HTTP-сервис принимает `POST /v1/chat/completions`
(OpenAI-формат, включая stream/tools) и внутри переводит в веб-протокол SaaS —
по сути (а) или (б) под капотом, но клиенту виден стандартный API. Всё, что
SaaS не умеет, шлюз эмулирует сам: tools через инъекцию схемы в системный
промпт + парсинг ответа (нативные `tool_calls`-сообщения Genspark отбивает
HTTP 422), параллельные вызовы — по одному за реплику; стрим — буферизацией.

**Живые примеры:** `deanxv/genspark2api` (695★, обновлён 2026-10-31; docker,
cookie-пул с round-robin и авто-переключением при сбое, `/chat/completions`,
`/images/generations`, `/videos/generations`), `xinxinshuhao-create/genspark2api`
(28★; мульти-аккаунтный round-robin, эмуляция tools, `/health` по аккаунтам),
`chnd372/genspark-gateway` (6★; «multi-account pool, 57 models, dashboard»).

**Хрупкость (в):** наследует (а)/(б) плюс свои слои: эмуляция tools —
вероятностная (модель может не выдержать контракт вывода), буферизация стрима
ломает «живой» поток при tool-запросах, карта «модель↔чат» (deanxv:
без привязки модели к сессии Genspark сам переключает модель — «понижение
интеллекта»), лимиты пула (у xinxinshuhao: 6 req/min, 60 req/ч на аккаунт,
429 при 3+ параллельных, восстановление ~30 с).

**Требования к среде (в):** docker/процесс + cookie-пул + опционально
playwright-прокси для v3 + egress-изоляция на аккаунт (рекомендация обоих
проектов: аккаунты с одним IP ограничиваются вместе).

## 3. Предтечи в нашем стеке

### 3.1 ADR-021 / шим justwoker (2026-10-07) — прямая предтеча паттерна (в)

Факты (01-Reference/provider-cards/justwoker.md; session-log 2026-10-07):
justwoker (New API-шлюз) регрессировал на стриминговом anthropic-пути — SSE без
content-блоков, OpenCode отвечает пустотой. Оператор поднял локальный шим
(Bun, systemd-unit `justwoker-shim.service`): принимает stream-запрос OpenCode →
форвардит upstream non-stream → сам генерирует корректный SSE
(content_block_start/delta/stop, включая tool_use). OpenAI-фасад — в шиме.
opencode.jsonc смотрит на `http://127.0.0.1:<PORT>/v1`. Крэш-гвард dee6f15
закрыл краш при отмене клиента; далее — клиентский socket-idle (Bun
BUN_CONFIG_HTTP_IDLE_TIMEOUT, фикс `timeout:false`, потолок 600→900 c).
Когда стрим-регрессия апстрима ушла (2026-10-09), шим стал **опциональным
мостом**, целевое состояние — канал New API.

**Чем наш случай похож:** та же анатомия — «источник моделей без удобного для
нас контракта → локальный шим с совместимым фасадом → каталог видит обычного
провайдера»; тот же принцип «шим — временный мост, целевое —native-канал»
(для Genspark native-канала нет вовсе, поэтому шим-фасад там не переходное,
а постоянное решение, если владелец примет TOS-риск).

**Чем отличается:** justwoker — легальный API-провайдер с деградацией контракта;
мы чинили транспорт. Genspark — сознательный обход отсутствующего API с сессией
человека: добавляются слои cookie/TLS-имперсонации/captcha, которых в ADR-021
не было, и TOS-риск, которого не было совсем. Опыт шима переносится как
инженерия (SSE-пересборка, crash-guard, idle-timeouts, health-контур), не как
юридическая рамка.

### 3.2 Локальный GitHub MCP Server с PAT — предтеча по рамке доверия

Факт (06-Audits/2026-08-03-dv-hub-phase-d-audit.md, строка ~158): GitHub MCP
подключён локально с `${env:GITHUB_TOKEN}` (PAT владельца), `enabled: true`.
Сходство: доступ к чужому сервису не через публичный API-контракт агента, а
через личные креды владельца, резолв из env, без секретов в репо.
Отличие: у GitHub есть официальный API и PAT — это санкционированный создателем
сервиса путь; TOS-риска нет. Genspark-мост с PAT-аналогией совпадает только
гигиеной секретов (Ворота/env, вне репо) — не легальностью доступа.

Вывод: наш стек уже дважды делал «мост к чужому сервису под своими кредами» —
инженерная часть знакома; принципиально новое в кейсе Genspark —
антибот-контур и TOS-риск аккаунта.

### 4.1 ToS (April 2, 2026) — релевантные пункты (цитаты дословно)

1. Автоматизация/скрейпинг — прямой запрет, шире чем «не скрейпи»:
   «You hereby agree to refrain from conducting any systematic or automated
   data collection activities, including scraping, datamining, extraction, or
   harvesting, either on or in relation to the Service. Such prohibited
   activities include, but are not limited to, **utilizing the Service as an
   input for other services, websites, or databases**.»
   → Мост «Genspark → наш ротатор/агенты» подпадает дословно: сервис как вход
   для другого сервиса. Это ключевой пункт аудита.
2. Reverse engineering: «Any unauthorized attempts to reverse engineer,
   duplicate, replicate, or illegally acquire intellectual property associated
   with the Service will not be tolerated and may lead to legal actions.»
   → реверс веб-протокола — формально под этим пунктом; реальное исполнение
   у сервиса — приостановка аккаунта (см. п.4), юридическая эскалация —
   теоретическая, но заявлена.
3. Аккаунт — личный: «You agree not to share, transfer, or sell your Account...
   not to share your Account or password with anyone else or allow access to
   your Account to anyone else.»
   → Мост технически «даёт доступ к аккаунту» не-человеку. Это касается ЛЮБОГО
   аккаунта — и отдельного тоже: Р-072 снижает ущерб от санкций, но не делает
   мост TOS-чистым. Честная формулировка: зонд с отдельного аккаунта —
   управляемый TOS-риск, а не легальная лазейка.

4. Санкции: «We reserve the right, in our sole discretion, to restrict, suspend,
   or terminate your access... at any time and for any reason» + при терминации
   за нарушение — «you may not be entitled to any refund». Риск материальный и
   односторонний; обжалование — поддержка, не суд.
5. Юрисдикция: California, AAA arbitration, отказ от class action —
   практической защиты у пользователя мало; для нас главное — не доводить.

### 4.2 Fair Use Limit (helpcenter/membership-plans, Nov 3, 2026) — три запрета дословно

«Prohibited activities include:
- Automatically or programmatically extracting data in bulk
- Sharing your account credentials or making your account available to others
- Reselling access or using Genspark to power third-party services»

И рядом, в секции Commercial use: «No scraping. Our Terms of Service also
prohibit scraping or other automated extraction from Genspark, including using
the Service as a data source for other services, websites, or databases.
**This limits how you access Genspark, not where you can use your outputs.**»

Разбор по-честному: оговорка «limits how you access, not where you use
outputs» описывает легальную зону — пользоваться результатами можно где угодно.
Серая зона моста: получить ответ для себя (агент владельца) через
нестандартный доступ. Три запрета Fair Use читаются против нас, если мост
будет: (1) выкачивать массово, (2) раздавать аккаунт «другим» (у нас один
контур-потребитель — аргумент в нашу пользу, но не гарантия), (3) «power
third-party services» — ротатор формально третьесервис. Прямого разрешения
этой схемы в TOS нет; есть только ничьё молчание.

### 4.3 Вердикт TOS-аудита

- **Мост к Genspark = нарушение ToS/Fair Use по букве** (п. 4.1.1 + Fair Use).
  Не «запрещено скрейпить сайт» в узком смысле — запрещено использование
  сервиса как входа другого сервиса, и это ровно наш кейс.
- **Отдельный аккаунт (Р-072) — мера сдерживания ущерба, не легализация:**
  при санкции теряется бесплатный/дешёвый аккаунт, не платная подписка
  владельца. Платный аккаунт владельца под любой автоматизацией — запрещён
  каноном, и аудит это подтверждает как правильное решение.
- **Что усугубляет риск (из чужих проектов — не наша практика):** массовая
  авторегистрация аккаунтов с решателем капчи (96–116 c/аккаунт в
  xinxinshuhao) — гарантированный профиль абьюзера; удаление следов диалогов
  (AUTO_DEL_CHAT у deanxv) — против нашего провенанс-канона.
- **Что снижает риск (профиль «вежливого зонда»):** один валидированный
  аккаунт, антропогенные темпы (без батчей), без обхода капчи (капча = стоп),
  без чувствительных данных (Р-Д-006), полная история зондов у нас.
- Санкции ожидаемо технические: rate-limit → 429 → приостановка аккаунта;
  юридическая эскалация для единичного некоммерческого зонда маловероятна —
  это оценка (не факт), помечена как мнение ИПТ.
- Политика недоступных/неясных зон: нет — политика прочитана целиком из
  первоисточников; неясность только в отсутствии явного разрешения мостов
  (серая зона, см. 4.2).

## 5. Границы перехода: зонды → кандидат → ротация

Ведомственная развилка (Р-068): ИПТ исследует, Ротатор (УАС) канонизирует
пороги и держит ротацию, ИС/Лаба инкубирует шлюз. Пороги ниже — **предложение
ИПТ** на базе живого bench-gate УАС; канонизирует Ротатор своим словом/решением.

**Ступень 0 — валидация аккаунта (Р-072 п.5, без неё не зондировать):**
(1) существование — вход в UI с отдельного аккаунта рукой владельца;
(2) активность — один диалог рукой; (3) лимиты — чтение лимитов/кредитов в UI.
Фикс: три факта в журнале (кто/когда/что видел), секретов ноль.

**Ступень 1 — зонды (разрешены Р-072, отдельный аккаунт):**
- только smoke-тексты и меты (Р-Д-006): «ответь ok», счётчики, коды ошибок;
- read-only там, где возможно; антропогенные темпы; капча/челлендж = стоп-сигнал
  прогона, не обходить;
- классификация по канону УАС: ACTIVE / DEGRADED / BLOCKED / ERROR / SKIPPED,
  запись в `provider-health.jsonl` c `source=probe-genspark` и меткой
  `probe_mode_only` (как сейчас: строка-заглушка frame остаётся);
- длительность: устойчивость = 3 прогона в 3 разных дня без BLOCKED/ERROR.

**Порог «зонд → кандидат»** (предложение, bench-gate УАС
«probe ACTIVE → model-bench PASS → канал»):
1. устойчивые зонды: 3/3 дней ACTIVE (см. выше);
2. известные лимиты: RPM/RPD/кредиты измерены и внесены (DoD-5 Ротатора:
   «квоты не жгутся вслепую»);
3. качество подтверждено: model-bench PASS (k≥1) на целевой модели + замер
   tool-call-стабильности (урок verifier-канала 10-31: 1/3 пустых tool-вызовов
   = не кандидат на tool-heavy роли);
4. TOS-рамка принята: слово владельца на риск отдельного аккаунта (после §4);
5. наблюдение EOL: модель доступна ≥2 недель без «мигания» каталога.

**Порог «кандидат → ротация»** (предложение; канонизирует Ротатор):
1. кандидат прошёл bench-gate (все 5 условий выше);
2. шлюз-инкубация (ИС/Лаба) даёт устойчивый OpenAI-фасад: health-эндпоинт,
   crash-guard, idle-timeouts — опыт ADR-021 переносится как чек-лист;
3. failover-протокол Лабы (docs/specs/lab-rotator-failover-protocol.md):
   сценарии F1 (429/quota→деградация), F2 (BLOCKED/ERROR→переезд),
   F3 (мёртвый ключ→fallback) — полнота 3/3, t_switch median ≤60 c /
   p95 ≤120 c, ложные переключения 0;
4. **отдельное слово владельца** (Р-072 п.3: ротация — только отдельным словом);
5. только после 1–4: внесение в `providers.json`/каталог.

**Канон-стража (Р-068, живой факт):** `providers.json` трогать нельзя до слова —
probe строит список из него, правка = фальшивая проба. Genspark в каталог не
вносится; статус держится строкой-заглушкой `source=frame` с `probe_mode_only`.
Роль «genspark» в `rotation.json` не создаётся до порога 5.

## 6. Нужно от владельца (списком, без додумывания)

1. **Отдельный аккаунт Genspark** — создаёт сам или поручает (вопрос уже стоит
   в портале, Р-072 п.6). Регистрацию не автоматизируем (см. §4.3).
2. **Тариф отдельного аккаунта** — решение с бюджетом:
   Free = 100 кр/день до пожизненного потолка (для моста почти бесполезен:
   чужие замеры 09-2026 — ~100 запросов на жизнь аккаунта, 6 req/min);
   Plus = от $24.99/мес (10k кр/мес, core-модели AI Chat без списания кредитов).
   Для зондов хватает Free; для смысла («доступ к последним моделям» как
   резервная ёмкость) нужен Plus — решает владелец.
3. **Доступы/секреты отдельного аккаунта** — только через Ворота
   (owner-gate.ask_secret), вне репо и журналов (Р-072 п.4).
4. **Слово на TOS-риск** — принять/не принять риск санкций на отдельный
   аккаунт с учётом §4 (Р-068: риск аккаунта — портал; Р-072 — рамка зондов).
5. **Слово «зонды → кандидат»** — после устойчивых зондов (порог §5).
6. **Отдельное слово на ротацию** — только после bench-gate + F1–F3 (§5).

Ничего сверх списка не нужно; никаких платных решений до п.4.

## 7. Красные линии (обе мандатные рамки)

- **Аккаунт владельца (msivyhin, платная подписка) — исключён из любой
  автоматизации** (Р-072 п.2). Никаких cookie/токенов/сессий с него.
- **Секреты — только через Ворота**, вне репо и журналов (Р-068, Р-072 п.4).
- **Разработка не начинается до permit** (Р-068): сегодня — исследование,
  спека и пороги; ни одной строки моста в контуре.
- **Зонды только с отдельного аккаунта**, и только после валидации
  существование → активность → лимиты (Р-072 п.5).
- **TOS-риск — решение владельца** (Р-068); ИПТ не принимает риск за него.

- **Без обхода капчи и массовой регистрации**: solver-пайплайны чужих проектов
  (2captcha и т.п.) — не наша практика; капча/челлендж = стоп прогона.
- **Без сокрытия следов**: AUTO_DEL_CHAT-подобные опции не включать;
  история зондов хранится у нас полностью (провенанс-канон).
- **Приватность проб (Р-Д-006)**: через мост не идут секреты, личные данные,
  содержимое приватных зон — только smoke-тексты, меты и счётчики.
- **Каталог/ротатор**: `providers.json`, `rotation.json`, `model-catalog.json`
  не трогаются до порога «кандидат → ротация» с отдельным словом владельца.
