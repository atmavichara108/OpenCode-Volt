# Двойной SDK — M Code и OpenCode TUI

## Принцип (решение Rudra, 2026-10-01)

**M Code и OpenCode TUI — два равных клиента к общему ядру**, а не иерархия
«дирижёр/исполнитель».

- Оба SDK открывают **одни и те же проекты**, читают **почти одинаковый
  агентский слой**.
- Подход пользователя — **тайловый мультиплексор: максимум автономности,
  минимум GUI**. Pip-Boy построен на этих принципах и **использует OpenCode
  внутри себя**.
- Поэтому SDK должны быть **равнозначны (более-менее)**: нет постоянного
  «главного». Различие — в интерфейсе и месте запуска, не в роли.

## Общее ядро (shared kernel)

Что разделяют оба SDK:

| Слой | Где | Владелец SSOT |
|------|-----|---------------|
| Агенты (librarian, build, …) | `dotfiles/opencode-global/.config/opencode/` + проектные `.opencode/` / `.mcode/` | dotfiles (единый источник) |
| Провайдеры | `dotfiles/.../opencode.jsonc` | **dotfiles — единый SSOT** |
| Проекты | репозитории на диске | сам проект |
| Протокол координации | git-дерево (TASKS.md, claims, ветки `task/*`, spec-home) | git |
| Память/индекс волта | `04-Memory/`, `00-INDEX.md` | волт |

## Два клиента

| | M Code | OpenCode TUI |
|---|---|---|
| Форма | Desktop (AppImage, форк OpenCode Desktop) | TUI, тайловый |
| Место | автономное окно | **встроен в Pip-Boy** |
| Интерфейс | минимум GUI | чистый текст/тайлы |
| Конфиг-источник | `$GLOBAL = m-code-data/config/mcode.jsonc` | dotfiles `opencode.jsonc` |
| Данные | `m-code-data/mcode/mcode.db` (1.8GB) | `~/.local/share/opencode/opencode.db` (2.4GB) |
| API | 32 пути, **нет** `/prompt`/`/synthetic` | 115 путей, есть `/prompt`/`inbox`/`synthetic` |
| Роль | равный клиент | равный клиент |

## Координация (как не конфликтуют)

Раз SDK равнозначны и читают один агент-слой, сессии M Code и OpenCode — это
сессии **одних и тех же агентов в разных оболочках**. Координация — не через
иерархию, а через **общий протокол**:

1. **git-дерево = SSOT состояния.** `TASKS.md` (что делается), claims (кто
   держит зону), ветки `task/*` (изоляция потоков), `spec-home` (канонические
   спеки). Кто открыл проект в своём SDK — тот и работает, но результат
   кладёт в дерево, которое видит другой SDK.

2. **Асимметрия API (факт, не решение):** M Code → OpenCode через OpenCode
   HTTP-API (`POST /api/session/{id}/prompt`) работает; OpenCode → M Code —
   нет (у M Code нет `/prompt`). Поэтому живой двусторонний обмен поверх API
   недоступен; **дерево остаётся основным каналом** для обоих направлений.

3. **Оркестратор — динамический, не фиксированный.** Кто в конкретной
   сессии дирижёр (ставит задачи, ведёт роутинг) — решает контекст, не тип
   SDK. Librarian в M Code может ставить build-задачу в OpenCode; OpenCode-
   агент может записать результат в дерево для librarian.

## Место M Code в экосистеме

- M Code — **Desktop-центр** (его `$GLOBAL` — стратегический конфиг волта,
  librarian там).
- OpenCode TUI — **тайловый слой Pip-Boy**, исполнитель проектного/агентского
  слоя, живёт на dotfiles SSOT.
- Оба — **равные равноправные клиенты** общего ядра. M Code не «выше» и не
  «ниже» OpenCode TUI; они — два окна в одну систему.

| Вопрос | Решение |
|--------|---------|
| Роль SDK | Равнозначны (не «дирижёр/исполнитель») |
| SSOT провайдеров | **dotfiles = единый источник** |

## Согласованный диагноз провайдеров (с OpenCode-сессией, 2026-10-01)

Сверено с OpenCode-сессией `ses_f0ce48108ffe85P9el6vABEvIA` («Модели падают в
мкоде но работают в опенкоде»). Единого дефекта нет — каждый провайдер падает
по-своему, и «работают в OpenCode» ≠ M Code сломан: это **разные каналы**.

| Провайдер / модель | Симптом | Причина |
|---|---|---|
| apinex / `free/claude-opus-4.6` | 402 billing_error | **модель платная** (под подпиской apinex), не «лимитов нет» |
| nvidia / `moonshotai/kimi-k3` | 401 Unauthorized | NVCF-ключ нигде в открытом виде нет |
| justwoker / `claude-opus-4-8` | 403 Cloudflare | провайдер BLOCKED (как в памяти) |
| amd-radeon / `DeepSeek-V4-Flash` | StreamIdleError | таймаут простоя 5 мин |
| `opencode-go/glm-5.3-flash` | работает только в OpenCode | free-канал OpenCode (models.opencode.ai), **M Code не имеет opencode-go** |

**Корень различия каналов:** M Code хранит ключи в **secret-service** (system
keyring, sealed, через UI) и **не загружает vault `.env`** (AppImage, direnv не
срабатывает). OpenCode TUI — ключи из **открытого `auth.json`** + vault `.env`
(запуск из терминала с direnv). Плюс SSOT-корень (см. выше): M Code ищет
`mcode.json(c)`, dotfiles даёт `opencode.json(c)` → провайдеры dotfiles M Code
игнорирует. OpenCode в основном работает через `opencode-go` + `anymodel`
(ключи в открытом auth.json) — стабильные каналы, которых у M Code частично нет.

## Открытые вопросы (следующий раунд)

1. **Сессии за один каталог:** если два SDK открывают один проект одновременно
   и оба создают сессии — как они не дерутся за рабочий каталог/ветки? Сейчас
   решается ветками `task/*` + claims; нужен ли жёсткий протокол (лок на проект)?
2. **Пустой `m-code-data/opencode/opencode.db` (6MB)** — зачем создан, кто пишет,
   можно ли убрать (вероятно, когда opencode CLI запускался в M Code env).
3. **Орфан `opencode serve --service`** — завести в штатный сервис или перезапуск
   вне менеджера намерен (вопрос к dotfiles).
4. **Агент-слой дублирован (`.opencode/` vs `.mcode/`)** — решение «оставить как
   есть» временное; при росте — унифицировать через симлинки на dotfiles.
