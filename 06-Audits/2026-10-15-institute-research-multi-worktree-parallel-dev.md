# Параллельные контейнеры через несколько git worktree в dotfiles

Read-only исследование Института Передовых Технологий. Ничего не внедрялось:
dotfiles не правился вообще, основной checkout волта не тронут. Каждая внешняя
практика и каждый технический факт проверены живым веб-поиском 2026-10-17
(источники с URL и датами — в разделе 14). Выход исследования: вердикт о
применимости, кандидат в ADR текстом (раздел 10), черновик порядка работы
(раздел 11), критерии штатности (раздел 12) и открытые вопросы (раздел 13).
Внедрение — только по отдельному слову Rudra.

## 1. Мандат и провена

Мандат — заявка sysop dotfiles по поручению Rudra от 2026-10-15: тикет И-52
«Параллельные контейнеры через несколько git worktree (2–3 одновременно) —
снять ограничение "одна активная ветка на всех"», отправлен в Институт
(scope research-worktree-parallel, доставлено seq=2294). Диспозиция Центрального
Узла ref ippt-pace-20261017: трек подтверждён владельцем, второй в конвейере,
отчёт — письмом ЦУ. Провена прогона: работа велась в именованном worktree
волта на ветке `task/institute-wt-parallel-20261015` (каталог
`/tmp/opencode/vault-tasks/institute-wt-parallel-20261015`), перед публикацией
ветка синхронизирована с origin/main; артефакт пишется в волт, кандидат в ADR —
текстом внутри артефакта, файл решений dotfiles не правится.

## 2. Контекст-факт заявки (basis: quoted)

Дословно из заявки (sysop, по поручению Rudra, 2026-10-15):

> «В dotfiles один checkout и одна активная ветка на всех. При параллельных
> сессиях контейнеры конфликтуют файловыми зонами и переключают worktree друг
> под другом. Сегодняшний инцидент: три коммита sysop уехали на чужую
> волновую ветку, дерево было переключено под ним. Правило не более трёх
> активных отсеков в реестре есть, но технически всё упирается в одну рабочую
> копию.»

Мотив из тикета И-52: «инцидент гонки — мои 3 коммита уехали на чужую
волновую ветку» (basis: quoted, inbox dotfiles). Свежие замеры числа деревьев
(диспозиция ЦУ, проверено мною 2026-10-17): 2026-10-16 в dotfiles было 8
worktree (6 живых плюс 2 остаточных: detached prunable в зоне `/tmp/mcode` и
временное дерево Института); 2026-10-17 — 4 (замер подтверждён: основное
дерево на ветке `task/next-20261016`, плюс деревья `lab-l9-20261015`,
`i53-lineage-20261016`, `t179-activity-collector`). Число живых деревьев скачет день ото дня — каждое
переселение ветки физически переключает ветку основного дерева под всеми, кто
в нём работает: один checkout = одна активная ветка на всех, и это корень
всех трёх инцидентов недели.

## 3. Резюме и вердикт

Вердикт: применимо. Схема «отдельная папка на контейнер, своя task-ветка»
работает в dotfiles при трёх условиях: (1) контейнер — временный, на период
параллельной разработки, а не постоянный дом сессии; (2) stow-слой остаётся
в единственном main-дереве, из контейнеров ничего не стоуится; (3) рождение
и смерть контейнера видны в claims/ledger (И-51, ADR-028), а уборка идёт
только по полным именам. Это не противоречит отвергнутому ADR-014 п.5:
там отвергнут постоянный worktree-на-сессию, здесь — времянка на период
параллельности при сохранении stow-канона; разбор различия — в разделе 9.
Рекомендуемый потолок: 2–3 контейнера одновременно (как и просил И-52),
сверх — только по отдельному слову владельца.

## 4. Вопрос 1: применимость схемы и совместимость со stow

### 4.1. Схема

Контейнер = временное именованное рабочее дерево (linked worktree) dotfiles в
отдельном каталоге (как минимум вне основного чекаута; фактически у нас уже
есть устоявшиеся зоны `/tmp/opencode/vault-tasks` для волта и
`dotfiles-tasks` для dotfiles) на собственной ветке вида `task/<слаг>`. Схема
создаётся от свежего origin/main, живёт на время параллельной разработки,
публикуется мержем в main и убирается по полному имени. Основное дерево
остаётся единственным местом, где живёт stow-слой и куда указывают симлинки
домашней директории.

### 4.2. Физика git: что изолируется, а что нет

Ключевой внешний факт (документация git-worktree, проверено 2026-10-17):
worktree даёт собственную рабочую директорию, собственный индекс и
собственный HEAD; всё остальное общее — хранилище объектов, refs, config,
hooks, reflog веток. Одна ветка не может быть чекаутена в двух деревьях
одновременно (без флага силы) — это защита, а не неудобство: она исключает
гонку за ref ветки. Таблица для нашего случая:

| Объект | В контейнерах | Следствие для dotfiles |
|---|---|---|
| Рабочие файлы, индекс, HEAD | свои в каждом дереве | переключения веток больше не происходят «под» чужой сессией |
| Объекты, refs, remote | общие | коммит в контейнере сразу виден всем деревьям |
| config (.git/config), hooks | общие | гейты pre-commit (branch/zone-mix) и claims веток действуют во всех контейнерах без настройки |
| Стек стэша (refs/stash) | общий | ловушка №1, см. разделы 7 и 8 |
| Блокировки config/index.lock | общие | ловушка №2: параллельное создание деревьев может конфликтовать на записи config |

Отдельно: «multiple checkout» git до сих пор помечает как экспериментальную
область (документация git-worktree, там же) — аргумент держать число
контейнеров малым и не выращивать зоопарк.

### 4.3. Три варианта stow-совместимости

Канон, из которого исходим: УАС-спека (approved Rudra 2026-10-17, Р-016),
раздел операционных стандартов, шов осиротения — дословно: «Общее дерево —
только короткие публикации через временное рабочее дерево; stow-слой
остаётся в main-дереве». Плюс ADR-017: stow признаёт только относительные
ссылки, созданные им самим. Варианты:

Вариант А. Стоуить только из main-дерева (рекомендуемый, соответствует
канону). Все симлинки дома продолжают указывать в единственный основной
checkout; контейнеры — чисто git-овые рабочие зоны, из них stow не
вызывается никогда. Плюсы: stow-модель не меняется ни на шаг; симлинки
не мигрируют; здоровье проверяется сухим прогоном из main-дерева; слияние
контейнера в main мгновенно делает изменения живыми в доме. Минусы: правки
конфигов в контейнере не видны в доме до мержа (для большинства сюжетов —
документация, инфраструктура агентов — это не минус, а норма); осознанная
цена за сохранение канона.

Вариант Б. Отдельный тестовый HOME для контейнера (опциональный пилот, не
входит в базовую схему). Из ветки контейнера stow разворачивается в
изолированный тестовый дом (каталог вне настоящего дома), приложения
запускаются с ним для проверки живого поведения до мержа. Плюсы: честное
сквозное тестирование ветки без риска для настоящего дома. Минусы: двойной
setup, риск зацепить лишнее в тестовый дом; для текущих сюжетов Института
и ИЦ избыточен. Пилот — только по отдельному слову Rudra.

Вариант В. Несколько stow-таргетов в живой HOME (отвергнут). Стоуить из
нескольких деревьев в один и тот же настоящий дом: конфликты владения
(«existing target is not owned by stow», ADR-017), перезаливка симлинков
по принципу «кто последний», дом, указывающий в несколько веток сразу.
Не вариант, а инцидент; фиксируется как запрет в кандидате ADR.

### 4.4. Внешние подтверждения варианта А

Живой пример «stow живёт в main-дереве, остальные деревья — рабочие зоны»
существует в индустрии: репозиторий Yarden-zamir/dotfiles (проверен
2026-10-17) использует раскладку bare плюс worktree-контейнер: git-репозиторий
лежит в служебном каталоге, основной рабочий checkout «main» одновременно
является stow-пакетом и единственной точкой $DOTFILES, а локальные
неотслеживаемые файлы (секреты, окружение) расшариваются в новые деревья
post-checkout-хуком. Инструмент git-worktree-tools (jeansimeoni, проверен
2026-10-17) решает ту же проблему симлинками неотслеживаемого состояния
(.env, каталоги агентов) из основного дерева — нам это не нужно, у dotfiles
такого состояния в пакетах нет, но сам паттерн «разделяй неотслеживаемое,
не разделяй stow-слой» подтверждён. Структурная альтернатива на будущее:
chezmoi рендерит файлы копированием, а не симлинками (документация chezmoi,
проверена 2026-10-17) — при такой модели второй checkout вообще не угрожает
дому; миграция с stow — отдельное решение вне этого исследования, упомянуто
только как ориентир, если симлинк-слой однажды станет узким местом.

## 5. Вопрос 2: взаимодействие с обвязкой

tree-hygiene. Гейты сконструированы под общий checkout и продолжают
работать: плагин блокирует переключение веток при грязном дереве, стэш без
сообщения, коммит вне task/*, смешение зон в одном коммите. Hooks общие
для всех деревьев (физика git), поэтому pre-commit действует в каждом
контейнере автоматически. Единственная правка канона: пункт 5 tree-hygiene
(«НЕ создавай git worktree для этого репо; изоляция = task-ветки в одном
checkout») — формулировка абсолютного запрета, введённая до появления
шва осиротения; кандидат ADR заменяет её управляемым исключением для
временных контейнеров при stow-слое в main-дереве. Формулировки гейтов
не меняются.

ship. Полный цикл /ship для контейнера не меняется структурно: preflight
через tree-cop, коммиты по зонам, sync с origin/main, мерж в main
без fast-forward, push, удаление своей ветки. Добавляется ровно один шаг:
после мержа — сухой прогон stow из main-дерева как health-check, и один
финальный шаг — уборка дерева контейнера по полному имени. Правило «свои
задачи в main через /ship» сохраняется дословно: контейнер публикуется
только через мерж своей task-ветки, никаких прямых пушей.

Реестр отсеков. Реестр (dotfiles, `.opencode/memory/registry.md`) остаётся
операционным окном видимости: контейнер открывается только строкой в реестре
(тема, владелец, ветка, файловая зона, состояние), как требует его правило 1.
Правило «один отсек = одна файловая зона» переходит из дисциплины слияний в
двойную защиту: зоны по-прежнему договорные (чтобы мержи не конфликтовали),
но физика деревьев теперь не даёт чужой сессии затереть твои файлы в твоём
дереве. Правило «не более трёх активных» сохраняется и покрывает контейнеры:
2–3 одновременно — это тот же бюджет, что и раньше, только теперь у каждого
своя папка.

И-51 и claims. Заявка sysop 2026-10-15 (принятая в inbox) уже требует
автозаписи claims при создании ветки/worktree (branch.<name>.owner и
claimedAt по ADR-019). Для схемы это не пожелание, а условие штатности:
у дерева не должно быть окна бесхозности. До внедрения И-51 — ручная запись
владельца в git-config при открытии контейнера (config общий на все деревья,
запись видна отовсюду). ADR-028 Lineage (approved 2026-10-17) уже даёт
механизм: ledger (рантайм-файл вне git-дерева, append-only, flock) с полем
worktree и dual-write claims (ledger — истина, git-config — читаемость).
Контейнеры обязаны записываться в оба места при рождении и отмечаться
merged/archived при закрытии — иначе lineage-audit ADR-028 будет честно
считать их слепыми зонами.

ADR-019. Владение веткой не меняется: claim в git-config чекаута, TTL 24
часа, гейт коммита в чужую живую ветку, обход только CLAIM_OK=1. Контейнер
не ослабляет ни один из этих гейтов — напротив, «владелец виден с момента
появления ветки» (шов осиротения) закрывает тот самый класс инцидента,
который мотивировал заявку: чужие коммиты на чужой волне были бы видны
до первого коммита, а не после.

## 6. Вопрос 3: ограничения платформы OpenCode

Одна БД сессий. Все деревья делят одно рантайм-состояние OpenCode: одну БД
сессий (таблицы session_v2 и worktree уже есть в ней — ADR-028 причисляет их
к шести реестрам), один каталог состояния. Сессия привязана к рабочей
директории: сессия контейнера живёт в директории контейнера, и это
предохраняет от «переключения под сессией» на уровне платформы — сессия
не переезжает в другую ветку вместе с деревом, потому что дерево не
переключается вообще.

Штатные инструменты. OpenCode имеет нативный набор: worktree_create (создать
именованный worktree, вернуть директорию), worktree_list (перечислить деревья
репозитория), session_move (перенести сессию в другую директорию — в том
числе текущую в новое дерево). M Code для субагентов умеет task с worktree
нативно (метод изоляции волта это уже фиксирует). Следствие для схемы:
открытие контейнера и переезд сессии — штатные операции, не самодеятельность;
сборку контейнеров надо вести через эти инструменты либо через прямой
git worktree add с записью в claims — главное не смешивать механики молча.

Агенты, плагины, скилы. Конфиг проекта грузится по рабочей директории:
сессия контейнера читает AGENTS.md и каталог .opencode из дерева контейнера,
то есть с ветки контейнера. Это одновременно возможность (инфраструктурные
правки агентов проверяются в контейнере изолированно) и риск (ветка,
отставшая от origin/main, даёт сессии устаревший набор агентов и гейтов; а ветка,
которая правит саму инфраструктуру, может менять правила у себя под ногами).
Лечение простое: контейнер создаётся от свежего origin/main и синхронизируется
перед стартом; это уже входит в порядок работы раздела 11.

peer-comms. Почта и рукопожатия адресуются по сессиям, не по деревьям:
контейнер не мешает каналу «на связи». Ledger ADR-028 уже включает поле
worktree — сшивка сессия/ветка/дерево не ломается.

## 7. Вопрос 4: риски — режимы отказа

Таблица «режим отказа → как распознаётся → что делает агент». Использованы
свежие инциденты недели (переключение дерева под сессией; коммиты на чужую
ветку; префиксный фильтр при уборке) и внешние свидетельства (разделы 8 и 14).

| Режим отказа | Как распознаётся | Что делает агент |
|---|---|---|
| Переключение дерева под сессией (коренной инцидент заявки: три коммита уехали на чужую волновую ветку) | git status показывает не свою ветку; владелец в branch-конфиге чужой; heartbeat соседа жив в handshake | Стоп, ничего не коммитить; доложить; свои коммиты спасать cherry-pick на свою ветку через rescue-ветку, не молча; впредь — контейнер, у дерева свой HEAD |
| Коммит на чужую ветку (та же гонка, вид снизу) | diff по стату против своей ветки перед коммитом (ADR-014 п.2); гейт 4 pre-commit по живому claim | Стоп на гейте — сигнал, не помеха; перенос коммита в свою task-ветку; отчёт постфактум |
| Общий стек стэша: pop в контейнере вытягивает чужой стэш | git stash list показывает записи «On <чужая ветка>»; чужие пометки в сообщениях стэшей | Не пользоваться стэшем в контейнерах вообще; спасение — именованная rescue-ветка (канон шва осиротения); незакоммиченное своё — коммит в свою ветку |
| Остаточные деревья плодятся (8 → 4 за сутки; detached prunable в `/tmp/mcode`) | git worktree list содержит имена без живого claim/ledger-записи; ветки смержены; записи старше TTL | Уборка по полному имени из собственного списка создания; никогда по префиксу; перед сносом — статус дерева; force — только по подтверждению владельца |
| Префиксный фильтр при уборке задевает чужой контур (инцидент 2026-10-14) | в кандидатах на удаление появились пути, которых нет в моём списке создания | Мгновенный стоп; чужие имена — остановка, а не фильтрация; доложить ЦУ; правило закреплено в УАС-спеке |
| Конфликт блокировок config при создании деревьев (внешний факт: worktree add пишет tracking-config в общий .git/config) | ошибка блокировки config.lock при параллельном создании | Не создавать деревья параллельным залпом; повторить последовательно; это аргумент за потолок 2–3 |
| Ветка уже занята другим деревом | git отказывает: ветка уже чекаутена | Контейнеру — своё имя (task/<слаг>), не поднимать занятую ветку, без force |
| Сессия осталась без директории (дерево снесено при живой сессии) | сессия указывает на несуществующий путь | Сначала session_move в живое дерево, потом уборка; перед сносом — сверка сессий по директории |
| Устаревшие агенты/гейты в контейнере (ветка отстала) | ветка позади origin/main при открытии; инфраструктурные файлы отличаются от main | sync с origin/main до старта работы; порядок раздела 11 делает это обязательным шагом |
| Stow-здоровье после мержа | сухой прогон stow из main-дерева сыплет ошибками владения | Чинить только в main-дереве, руками в контейнер не возвращаться; ADR-017: разбор через readlink, не флагами |

## 8. Вопрос 5: практики индустрии и что из них применимо

Worktree-на-задачу против worktree-на-агента. Сложившийся в 2026 году канон
(гайд Augment Code от 2026-04-07, проверен 2026-10-17): эфемерным задачам —
дерево на задачу (агенты назначаются на деревья, деревья не принадлежат
агентам постоянно); долгоживущим исполнителям с тёплым окружением — дерево
на агента. Наш случай — первый: контейнер на задачу/контейнер на волну,
сессия не привязана к дереву навечно. Промышленные команды гоняют 2–5
параллельных агентов без инфраструктуры и больше 10 с оркестратором;
совет индустрии — стартовать с 2–3 и масштабировать только после обкатки
паттернов координации. Это ровно потолок И-52.

Харнесы уже встроили worktree в продукт. Claude Code: флаг запуска сессии
в worktree, каталог деревьев по умолчанию, периодическая уборка, изоляция
субагентов деревьями, копирование неотслеживаемых файлов по списку
(документация Claude Code, проверена 2026-10-17). Codex/ChatGPT: сессии в
worktree, detached HEAD по умолчанию, handoff между локальным чекаутом и
деревом, различие управляемых и постоянных деревьев (документация Codex,
проверена 2026-10-17). Вывод: жизненный цикл деревьев под сессиями — уже
штатная функция агентских харнесов, не экзотика; наш Институт и Лаба уже
живут в именованных деревьях волта с 2026-10-14.

Дисциплина, которую индустрия считает обязательной. Разметка владения
файлами до старта (задачи с пересекающимися файлами — последовательность,
не параллельность); зелёный базовый прогон тестов до передачи дерева агенту;
мерж не сырым наложением, а через видимые конфликты (git сам показывает их
при мерже); rerere для повторяющихся конфликтов; разбор больших фич цепочками
малых (stacked diffs — их наш аналог: цепочки task-веток и мерж-очередь
/ship; внешний референс — статья Zylos Research от 2026-05-21 о стеках PR,
проверена 2026-10-17). Монорепо-приёмы (sparse checkout) нам не нужны —
репозиторий мал.

Ловушки, подтверждённые внешними первоисточниками. Общий стек стэша —
главная: refs/stash общий на все деревья, pop берёт верхушку чужого стэша;
дважды независимо подтверждено (замеры Amit Kothari на git 2.50.1 от
2026-07-29 и issue github/copilot-cli#1725 от 2026-02-27; оба проверены
живым поиском 2026-10-17); наш канон шва осиротения (rescue-ветка вместо
стэша) уже закрывает эту ловушку — остаётся запретить стэш в контейнерах
словом правила. Гонки записи: параллельные git-операции в нескольких деревьях
могут конфликтовать на config.lock и reflog (разбор TildAlice от 2026-04-12,
проверен 2026-10-17) — лечится малым числом деревьев и несвалом git-команд
в один миг. Защита git от самого себя: удаление дерева с незакоммиченными
изменениями без силы невозможно — эмпирика нашего инцидента 2026-10-14
совпадает с внешним опытом: git подстраховывает там, где ему позволяют
(вывод Kothari).

Альтернативы схеме. Очередь задач через один checkout — сегодняшняя модель;
она не ломается, пока задачи короткие и сессии не параллелят, но заявка
фиксирует её отказ под нагрузкой. Флаги возможностей (trunk-based в большом
масштабе) — неприменимы: у dotfiles нет рантайма со флагами, «всегда
живой main» у нас и так канон (stow-слой в main-дереве). Полные клоны —
избыточны (дублирование истории, повторные стягивания с remote), отвергнуты и внешней
практикой. Стэки задач — применимы как дополнение (зависимые сюжеты
последовательно цепочкой веток), не как замена контейнерам.

## 9. Стыковка с каноном

ADR-014 п.5 и ADR-019: что именно было отвергнуто. Оба решения отвергли
«git worktree на сессию» — постоянное проживание каждой сессии в своём
чекеуте. Причина: stow-симлинки живут в одном checkout; постоянная схема
превращает остальные деревья в мёртвый для stow вес и требует мигрировать
симлинк-ферму при каждом старте сессии. Кандидат этого не делает: он
предлагает временный worktree-на-контейнер на период параллельной разработки;
stow-слой остаётся в единственном main-дереве всегда, ферма симлинков
не мигрирует ни разу. Прямых противоречий нет — есть развитие: запрет
п.5 сужается с абсолютного до «постоянные деревья запрещены, временные
контейнеры — по правилам ADR-030».

Шов осиротения (УАС-спека, approved 2026-10-17, Р-016). Канон уже принял:
долгоживущие ведомства живут в именованных рабочих деревьях на своих
task-ветках; общее дерево — только для коротких публикаций через временные
деревья; stow-слой остаётся в main-дереве; спасение — именованная rescue-ветка,
не стэш; claims пишутся автоматически при создании ветки/дерева. Исследование
стыкуется с этим швом напрямую: контейнеры — это тот же класс временных
деревьев, распространившийся на саму разработку dotfiles; кандидат лишь
дописывает к шву потолок, зоны и порядок уборки.

ADR-028 Lineage (approved 2026-10-17). Ledger — рантайм-файл вне git-дерева,
append-only, под flock, один канонический путь для всех рабочих копий; поля
записи уже включают worktree и ветку; claims.jsonl мигрирует к этому канону
(dual-write: ledger — истина, git-config — читаемость); аудит видит orphan-
и stale-деревья. Контейнеры обязаны писаться в ledger при рождении и
отмечаться при закрытии; никакого второго ledger-механизма не заводится —
это было бы нарушением границы «никаких временных механизмов». Автозапись
claims И-51 поглощается слоем 1 ADR-028 — кандидат ссылается на неё, не
дублируя.

Реестр отсеков и решения Р-014/Р-015. Реестр отсеков — операционный слой
Инженерного Центра (Р-015), реестр манифестов — юридический слой УАС (Р-014);
они не сливаются. Контейнер открывается строкой в операционном реестре
(тема, владелец, ветка, зона, состояние), а ведомство-владелец остаётся
тем, кем назван в реестре манифестов. Инциденты с деревьями — поток
Мастерской по методу incident-fix; исследование — в Институте; внедрение
кандидата — у ИЦ по спеке, если владелец одобрит.

## 10. Кандидат в ADR (текст; файл решений dotfiles не правится)

Название: ADR-030 «Временные worktree-контейнеры для параллельной разработки
dotfiles».

Контекст. В dotfiles один checkout и одна активная ветка на всех (basis
quoted, заявка sysop 2026-10-15, И-52). Параллельные сессии конфликтуют
файловыми зонами и переключают дерево друг под другом; инцидент 2026-10-15:
три коммита sysop уехали на чужую волновую ветку. Реестр отсеков ограничивает
активные темы тремя, но технически всё упирается в одну рабочую копию.
Постоянный worktree-на-сессию отвергнут (ADR-014 п.5, ADR-019): stow-симлинки
живут в одном checkout. Шов осиротения УАС-спеки уже канонизировал временные
деревья для коротких публикаций при stow-слое в main-дереве.

Решение. (1) Параллельная разработка dotfiles ведётся во временных
именованных worktree-контейнерах: отдельный каталог на контейнер, своя
ветка task/<слаг> от свежего origin/main. (2) Одновременно — не более трёх
контейнеров (штатный режим два-три); каждый открыт строкой в реестре отсеков
с темой, владельцем, веткой и файловой зоной; зоны контейнеров не
пересекаются. (3) Stow-слой живёт только в main-дереве: из контейнеров stow
не вызывается никогда; симлинки дома продолжают указывать в main-дерево;
здоровье проверяется сухим прогоном из main-дерева после каждого мержа.
(4) Рождение контейнера обязательно сопровождается записью владения:
claims по ADR-019 (branch-конфиг) и запись в ledger ADR-028 (поле worktree);
после внедрения И-51 это происходит автоматически, до того — вручную при
открытии. (5) Публикация — только через /ship: мерж своей ветки в main без
fast-forward, push; прямые пушы и коммиты в main запрещены, как и прежде.
(6) Уборка — только по полному имени из списка, составленного при создании;
никогда по префиксу; флаг силы — только по прямому подтверждению владельца.
(7) Стэш в контейнерах запрещён; спасение своей и чужой незакоммиченной
работы — именованные rescue-ветки (шов осиротения). (8) Создание деревьев —
последовательно, не залпом (общий config и его блокировки). (9) Долгоживущие
деревья ведомств (Институт, Лаба) — отдельный класс по шву осиротения, не
контейнеры; временный контейнер, переживший свою волну, закрывается либо
переоформляется строкой реестра.

Альтернативы. Оставить один checkout (статус-кво) — отвергнуто заявкой:
отказ под параллельной нагрузкой. Постоянный worktree-на-сессию — отвергнут
(ADR-014 п.5): навсегда размножает мёртвые для stow копии и миграцию
симлинков. Полные клоны репозитория — отвергнуты: дублирование истории,
плюс рассинхрон. Несколько stow-таргетов в живой дом — отвергнуто как
инцидентоопасное (ADR-017). Очередь задач без контейнеров — остаётся для
одиночных сессий, но не снимает гонку параллельных.

Последствия. Переключения веток под живой сессией в основном дереве
исчезают для контейнерных сюжетов; основное дерево освобождается под
main-ветку и короткие правки; конфликты переезжают из невидимого затирания
в видимые конфликты мержа; инцидентный класс «коммиты уехали на чужую
волну» закрыт физически, а не уговором. Цена: +1–2 рабочих каталога на диске
(копии рабочих файлов; объекты общие), дисциплина синхронизации контейнера
с origin/main перед стартом, обязательность записи claims/ledger, и
поправка формулировки пункта 5 tree-hygiene (абсолютный запрет заменяется
исключением этого ADR — отдельный коммит ИЦ после одобрения).

Границы. Действует только для dotfiles (в волте и обычных проектах уже
действуют свои режимы — метод изоляции волта и «для обычных проектов —
опционально» из ADR-019). Потолок три контейнера; сверх — слово владельца.
Никаких новых реестров: ledger, claims, реестр отсеков, handshake — всё
существующее. Код приложений не трогается. Тестовый HOME (вариант Б из
раздела 4.3) — вне этого решения, отдельный пилот. Префиксные уборки,
сила без подтверждения, стэш в контейнерах — запрещены навсегда.

## 11. Черновик порядка работы (при положительном решении)

Открытие контейнера. Шаг 1: sync — стянуть origin/main (fetch). Шаг 2:
создать именованный worktree от origin/main на ветке task/<слаг> — через
штатный worktree_create или прямой командой git; полное имя каталога
записать в свой список созданного (он же whitelist уборки). Шаг 3: записать
владение — branch-конфиг ветки (владелец, отметка времени) и строку
в ledger с полем worktree; до внедрения И-51 оба шага руками. Шаг 4:
строка в реестре отсеков (тема, владелец, ветка, файловая зона, состояние
«открыт», дата) — без неё контейнера не существует. Шаг 5: сессию
привязать к каталогу контейнера (session_move, если сессия уже живёт
в другом месте). Шаг 6: убедиться, что конфиг контейнера свежий (ветка
от origin/main, infra-файлы актуальны). Шаг 7: работать только в своей
файловой зоне; один коммит — один сюжет; гейты общие и уже действуют.

Правила зон во время работы. Зоны контейнеров не пересекаются (правило
реестра отсеков); пересечение нужно — сначала договор письмом через ЦУ,
затем переоформить строки реестра. Контейнер синхронизируется с origin/main
перед каждым мержем и при подозрении на отставание; стэш не используется,
незакоммиченное своё живёт в ветке, чужое спасается rescue-веткой. Ни один
вызов stow из контейнера не делается.

Закрытие контейнера. Шаг 1: довести ветку до готовности, синхронизировать
с origin/main, разрешить конфликты в своей ветке. Шаг 2: публикация через
/ship — полный цикл: preflight копа, мерж в main без fast-forward, push,
удаление своей ветки изнутри основного дерева. Шаг 3: health-check —
сухой прогон stow из main-дерева; ошибки разбираются там же, по ADR-017.
Шаг 4: убрать дерево по ПОЛНОМУ имени из своего списка создания; перед
удалением — статус дерева (сила — только по подтверждению владельца);
убедиться, что ни одна живая сессия не осталась в этом каталоге. Шаг 5:
записи — ревизия статуса в ledger (merged), claims по ветке гасятся вместе
с веткой, строка реестра закрывается с датой. Шаг 6: свежая task-ветка
для продолжения — по канону tree-hygiene, не оставаться в main.

## 12. Критерии успеха (когда схема считается штатной)

1. Stow не ломается: после каждого мержа контейнера сухой прогон из
   main-дерева чист; ни один симлинк дома ни разу не мигрирует и не
   указывает вне main-дерева; ни одного вызова stow из контейнера.
2. Claims пишется: у каждой ветки и дерева контейнера владелец виден с
   момента создания (branch-конфиг плюс ledger); после И-51 — автоматически;
   окно бесхозности не встречается ни разу за волну.
3. Переключений под сессией нет: за волну ни одного инцидента класса
   «дерево переключено под живой сессией» и «коммиты уехали на чужую
   ветку» в контейнерных сюжетах; HEAD основного дерева не меняется
   при переезде контейнеров.
4. Уборка чистая: после публикации число деревьев возвращается к базовому;
   ни одного удаления чужого или по префиксу; каждое удаление — по полному
   имени из списка создания.
5. Реестр сходится: lineage-audit (слой 2 ADR-028) не находит orphan-деревьев
   и stale-записей по контейнерам; heartbeat живых контейнеров свежий.

Внешние источники (живой веб, все проверены 2026-10-17):

- Документация git-worktree (git-scm.com/docs/git-worktree): один main-worktree
  плюс linked worktrees; одна ветка — одно дерево; общий config; per-worktree
  HEAD/индекс; lock/prune; «multiple checkout» экспериментально. Проверено
  2026-10-17.
- Amit Kothari, «What a git worktree does not isolate» (amitkoth.com,
  опубликовано 2026-07-29): refs/stash общий на все деревья (замер на git
  2.50.1); MERGE_AUTOSTASH per-worktree по случайности написания; per-worktree
  стэш через git stash store в refs/worktree; конфликты config.lock при
  worktree add (issue claude-code#47266, #34645); git worktree remove
  отказывается удалять грязное дерево без силы. Проверено 2026-10-17.
- Issue github/copilot-cli#1725 (опубликован 2026-02-27): глобальный стэш
  в worktree — перекрёстное заражение сессий; фиксируется через инструкцию
  агентам не звать git stash. Проверено 2026-10-17.
- TildAlice, «Git Worktree Race Conditions» (tildalice.io, 2026-04-12):
  три режима порчи (index.lock — безопасный отказ; reflog-гонки — тихая
  потеря; config — потеря настроек); лечение — последовательность git-операций
  и малое число деревьев. Проверено 2026-10-17.
- Документация Claude Code worktrees (code.claude.com/docs/en/worktrees):
  сессия в worktree, каталог по умолчанию, периодическая уборка, изоляция
  субагентов деревьями, копирование gitignored-файлов, baseRef fresh/head.
  Проверено 2026-10-17.
- Документация Codex/ChatGPT worktrees (learn.chatgpt.com): сессии в worktree,
  detached HEAD, handoff Local/Worktree, управляемые и постоянные деревья.
  Проверено 2026-10-17.
- Augment Code, «How to Use Git Worktrees for Parallel AI Agent Execution»
  (augmentcode.com, опубликовано 2026-04-07): worktree-per-task против
  per-agent; разметка владения файлами до старта; зелёный базовый прогон
  до передачи дерева; rerere; продакшен-команды на 2–5 агентов; отсутствие
  cross-worktree предупреждений о конфликтах. Проверено 2026-10-17.
- Zylos Research, «Stacked PR Workflows for AI Agent Collaboration»
  (zylos.ai, 2026-05-21): стеки малых PR, старт с 2–3 агентов, мерж-очереди;
  gh-stack (GitHub, апрель 2026) — нативные стеки. Проверено 2026-10-17.
- Yarden-zamir/dotfiles (github.com): bare плюс worktree-контейнер, stow
  только из main-worktree, секреты расшариваются post-checkout-хуком.
  Проверено 2026-10-17.
- jeansimeoni/git-worktree-tools (github.com): авто-симлинки неотслеживаемого
  состояния в новые деревья через post-checkout; сессии агентов различаются
  по директориям дерева. Проверено 2026-10-17.
- Документация chezmoi (chezmoi.io): рендер файлов копированием вместо
  симлинков; единый источник истины; структурная альтернатива symlink-слою.
  Проверено 2026-10-17.
