# Рубка управления: замеры runtime (WIP-1 закрыт)

Расшифровка (правило владельца): «SSE» — серверный поток событий в реальном
времени; «per-instance» — схема «у каждой сессии/окна свой серверный процесс»;
«token-budget» — наш журнал расхода токенов; «kill-criterion» — заранее
названная остановка; «median/p95» — медиана и 95-й перцентиль, cold-start
отдельно; «SSOT» — единый источник правды.

Методика: 20 прогонов на эндпоинт, read-only против боевого serve, пароль
сервиса только в переменной процесса (в артефакты не попал). WIP-канон:
один активный (этот); п.2 мандата (полигон прототипов) — в очереди до
отчётов Института/Служителя.

(кэшировать); полный список сессий — 1 МБ за опрос (поллинг раз в секунду =
60 МБ/мин — только кэш или delta-синхронизация).

## 2. Полнота списка сессий (бой с per-instance)

- Диск: session_v2 = **1909** сессий (+1092 legacy), сообщений 69.7 К (v2).
- API дефолт отдаёт **50** (newest, пагинация — задокументировано в openapi);
  `?limit=3000` → **1909 — точное совпадение с диском**.
- Фильтр `?directory=` работает (по проекту: ability-lab → 1).
- Топология сейчас: **один** serve --service (глобальный), 3 клиентских
  процесса. Сессии живут в общей БД — «единый список» достижим параметрами.

## 3. Свежесть health-моделей

- token-budget.jsonl (vault control-plane/telemetry): **3 записи, новейшая
  296.5 ч (~12.3 суток, 10-14)** — телеметрия по факту не ведётся; как основа
  health-панелей — протухла.
- incidents: 1165 json-файлов, новейший 0 ч — единственный живой источник.
- provider-health.jsonl Ротатора: СУЩЕСТВУЕТ в волте control-plane/telemetry — 112 записей, свежесть 12 мин (исправлено по сверке ЦУ 10-27; мой NOT-FOUND был ошибкой скоупа поиска — dotfiles вместо волта). Журнал живой: status/balance/latency_ms по провайдерам — health-модель СОБИРАЕМА.
- /api/provider: 18 провайдеров, поля — id/name/activation/settings;
  **лимиты/квоты отсутствуют** — подытверждает ИЦ: health-как-лимиты без
  своего слоя телеметрии недостижимы.

## 4. Поток событий (SSE)

- Подключение к глобальному /api/event — 8 мс; за 12 с при активной сессии —
  **1 событие (server.connected), ноль сессионных**.
- Причина: события сессий стримятся в их собственные per-instance процессы
  (TUI-каналы); глобальный serve их не транслирует; таблица event в БД пуста
  (истории событий нет).
- Следствие для панели: «живой поток» достижим только слушая экземпляры
  сессий или реконструкцией из БД (сессии/сообщения — да; события — нет).

## Сверка с ИЦ-досье: где право, где оптимистично

- **ИЦ право**: health-как-лимиты недоступны из API (подтверждено полями
  /api/provider); воротам в вебе нужна прослойка; безопасный паттерн
  «рубка-контроллер + ворота».
- **ИЦ оптимистично/неточно**: (а) «единый список сессий разных серверов НЕ
  доступен» — при текущей топологии доступен глобально (?limit; 1909=диск);
  риск реален только при схеме много-server; (б) «поток событий в реальном
  времени» из API-списка — глобально НЕ работает для сессий (см. §4) —
  это тонкое место, которого в досье нет; (в) «инциденты (11)» — по rglob
  *.json их 1165 (разный критерий счёта — факты за ИЦ).
- **Красная зона, которой нет в досье**: session/stats 3.4 с и event-история
  = 0 — панель «живых счётчиков» по этим данным не соберётся поллингом.

Не сработал. Ни один замер не потребовал платного/запретного; всё read-only.
