# Утилиты раскладки: И-54 (конвертер набранного текста) и И-55 (раскладко-независимые хоткеи)

Read-only исследование Института Передовых Технологий. Ничего не устанавливалось,
не настраивалось, не внедрялось. Каждый кандидат и каждый источник проверен живым
веб-поиском 2026-10-16—17 (даты в таблицах и в разделе 14). Внедрение любого
кандидата — только по отдельному слову Rudra; в конце исследования стоит вопрос
о постановке обеих утилит в очередь.

## 1. Мандат и провена

Мандат — заявка Инженерного Центра dotfiles (сессия-носитель
`ses_ece7b76c8ffeOkYZqZe38QbTVx`), по прямому указанию владельца от 2026-10-16.
Две категории: И-54 — конвертер уже набранного текста между русской и английской
раскладками по хоткею; И-55 — раскладко-независимые хоткеи (модификатор плюс
буква работает одинаково при русской раскладке). Провена прогона: работа велась в
отдельном worktree `task/institute-layout-tools-20261016` от `origin/main`,
основной checkout волта не трогался. Все численные данные (звёзды, лицензии,
даты коммитов и релизов, статусы issues) взяты из живого веба в момент проверки,
а не из памяти.

## 2. Слово владельца (basis: quoted, дословно)

> «есть опенсорсные утилиты которые 1 - когда текст набирается не на той раскладке, то по хоткею уже набранный текст переводиться в другую расскладку. то есть я пишу ghbdtn - нажимаю alt+e и слово превращается в привет. 2 - обеспечивает некую прокладку как бы дублируя символы из русской раскладки в латиницу, чтобы хоткеи во всех приложениях работали одинаково независимо от расскладки. пошли исследование таких утилит институту, потом выбери лучших и предоставь на решение поставить в очередь обе утилиты»

Из слова следуют три требования: только свободное ПО; обе категории решаются
отдельными инструментами; выход исследования — выбор лучших и вопрос владельцу
о постановке в очередь. Пример «alt+e» из слова владельца — иллюстрация принципа
«хоткей конвертации», а не требование конкретной клавиши: живые инструменты
используют жесты на чистых модификаторах (двойной Shift) или составные хоткеи.

## 3. Наш стек и три слоя проблемы

Среда (сверено по репо dotfiles): Manjaro Linux, X11 (не Wayland), Qtile,
Alacritty, zsh. Раскладка задаётся строкой в `qtile/.config/qtile/autostart-x11`
(строка 35): `setxkbmap -layout us,ru -option grp:alt_shift_toggle`. Скринлок —
`xss-lock -- /usr/local/bin/lock.sh` (строка 41). В баре есть виджет Systray
(`widgets.py`, строка 63) и виджет раскладки, опрашивающий `setxkbmap -query`
(`widgets.py`, строка 32). Кандидатам под трей место есть.

Боль И-55 на X11 существует потому, что хоткеи матчатся на трёх разных слоях,
и каждый слой реагирует на кириллицу по-своему (проверено 2026-10-16):

- Qtile сам: матчит нажатия по keysym текущей раскладки — подтверждение
  мейнтейнера в issue 4250 (qtile/qtile, 2023-05-04): «we convert the keycodes we
  receive to the current keyboard layout keysym, which we then match against
  your keybindings». При русской группе биндинг Super+q не срабатывает.
- Alacritty: не делает латинского резолва keysym — issue 7688
  (alacritty/alacritty): Ctrl+C/Ctrl+V при русской раскладке не работают,
  поддерживается обход через дополнительные биндинги с кириллическими keysym.
- Современные GTK- и Qt-приложения: решают проблему сами (резолв по «ascii»
  раскладке через scratch-состояние xkb — комментарий мейнтейнера libxkbcommon
  в issue 61, xkbcommon/libxkbcommon). Firefox и LibreOffice входят сюда.
- Остаточная зона риска: X-core-приложения, Java, сам qtile и Alacritty.

Отдельно: Xlib показывает «латиницу под Ctrl» только для текстовой строки
(скрытый контроль XkbLC_ControlFallback, включён по умолчанию), но keysym
приложениям уходит кириллический — это и есть корень проблемы (issue 61
libxkbcommon, ответ мейнтейнера). Готового «ctrl fallback» на уровне X-сервера
нет; kbvm (COSMIC) реализует его только у себя.

## 5. И-54 — механика конвертации и подводные камни на X11+Qtile

Два класса механики, и разница принципиальна для нашей среды:

- Класс «evdev+uinput» (lay-x11, easy-switcher, xswitcher): демон читает
  физические нажатия из `/dev/input/event*` и печатает через `/dev/uinput`,
  минуя X. Работает в любом окне, включая Flatpak и терминал. Цена: пользователь
  в группе `input` (группа читает ВСЕ нажатия системы, включая чужие сессии),
  плюс uinput-права через udev-правило или root. xswitcher называет себя
  «честным кейлоггером» прямо в README — самое честное описание класса.
- Класс «X11-native» (PolterType на X11): слушатель XInput2 и эмиттер XTest —
  всё внутри X-сессии пользователя, без групп, без root, без uinput. Для нашей
  рамки «нативно и легко, без демонов-кейлоггеров где возможно» это минимальные
  привилегии, достижимые для такой функциональности.

Подводные камни по кандидатам (проверено 2026-10-16—17):

- PolterType: измерен на Xfce, LXQt, Cinnamon, i3, icewm, openbox, fluxbox;
  qtile в списке измерений отсутствует, но стек тот же X11; MATE — единственное
  исключение (его демон настроек сам владеет раскладкой). Требует трей (у нас
  Systray есть). Встроенный апдейтер делает один сетевой вызов в сутки —
  отключается в конфиге. Проект молодой (42 звезды), но релизы еженедельные и
  документация честно описывает границы. При коррекции придерживает нажатия;
  за ремапером типа keyd сам отступает.
- lay-x11: единственный X11-форк свежего lay-public; группы зашиты в код
  (0 = us, 1 = ru) — совпадает с нашим порядком `us,ru`. Триггеры: двойной
  Shift по умолчанию, а также double-ctrl, double-alt, caps-lock, одиночные
  правые модификаторы и Pause. Список «не трогать» для команд терминала.
  Проблемы: форк опубликован одним днём 2026-05-11 и с тех пор не обновлялся;
  issues выключены (баг-репорт принять некуда); 8 звёзд — проверка в одиночку.
- easy-switcher: root-демон с системным юнитом и конфигом в `/etc` — для нашей
  рамки тяжеловат; сам README предупреждает о несовместимости с keyd и советует
  одноклавишное переключение раскладки. Оригинал спит с февраля 2025; форк
  megahanga (v0.4, июнь 2025) живее и добавил конвертацию выделения.
- xswitcher: самый мощный по конфигурируемости (регулярки по цепочкам событий),
  но «честный кейлоггер» с setuid-битом и сборкой через непринятый патч
  внешней библиотеки — трение выше выгоды для одного сценария.
- puny-switcher: идеологически чистый (не читает клавиатуру), но для хоткея
  ему всё равно нужен evdev-демон с запуском команд (kanata) — то есть класс
  проблем возвращается; в терминалах не работает (признано автором).

Отдельная находка, общая для всего класса И-54: инструменты с жестом Alt+Shift
конфликтуют с нашей опцией `grp:alt_shift_toggle` (переключение срабатывает
раньше жеста). Двойной Shift, принятый и в PolterType, и в lay-x11, с нашей
опцией не конфликтует. Более того, сама опция `alt_shift_toggle` ломает любые
хоткеи, начинающиеся с Alt+Shift — известный дефект XKB (issue 92 и 420
xkbcommon/libxkbcommon: переключение группы срабатывает по нажатию, а не по
отпусканию). Это дефект нашего существующего стека, а не кандидатов; выносится
в открытые вопросы.

## 6. И-54 — исключённые и неприменимые

- lay-public (родитель): лицензия Non-Commercial — не свободное ПО, отпадает
  по рамке «только свободное ПО», несмотря на активность (пуш 2026-10-16).
- xneur: мёртв давно, в брифе прямо запрещён к предложению.
- goswitch (Djarvur/goswitch, MIT): изящный без-root через IBus, но только
  GNOME Wayland — наш X11+Qtile не подходит.
- retypex (Lyssten/retypex): только Wayland/Hyprland.
- ReCast (orisup1/ReCast): пара английский-иврит, на Linux только Hyprland.
- kbcut (hhpmacedo/kbcut): это текстовые подстановки, не конвертер раскладки;
  интересен лишь как подтверждение, что X11 не даёт узнать активную группу
  через setxkbmap (нужен отдельный запрос состояния, как делает наш виджет).

## 7. И-55 — подход чистого xkb-варианта без демонов

Механика (ровно та, что предложил ИЦ): свой вариант русской раскладки, где
клавиша-буква получает четыре уровня — кириллица без Shift, кириллица с Shift,
латиница под модификатором, латиница под Shift с модификатором. За выбор
уровня отвечает кастомный тип клавиши в xkb, который сопоставляет нажатый
модификатор (Ctrl, Alt, Super) третьему и четвёркому уровням, а директива
сохранения модификатора (preserve) оставляет бит Ctrl/Super в состоянии —
иначе приложение увидело бы латинскую букву, но без модификатора. Приложение
получает честный латинский keysym с модификатором: хоткей срабатывает.

Рабочий референс существует и проверен автором на практике (unix.stackexchange,
вопрос 609605, «XKB Transparently map modifier level», проверено 2026-10-16):
автор описывает тип с картой Ctrl на уровень 3 и сохранением модификатора,
проверено на MPV, Dolphin, Gedit, LibreOffice, Firefox, ST плюс ZSH, ST плюс
NeoVim и Rofi; единственная оговорка — «не совсем хорошо работает в Chromium».
Это же решение хвалят мейнтейнеры keyd: в issue 852 (rvaiya/keyd) совет для
задач раскладки — «просто сделайте кастомную XKB-раскладку».

Размещение на X11 — главная инженерная тонкость (проверено 2026-10-16):

- Путь `~/.config/xkb` работает только для libxkbcommon, то есть для Wayland;
  официальная документация libxkbcommon прямо пишет: X-сервер имеет жёстко
  зашитые пути. Указанный ИЦ путь `/usr/local/share/xkb` в поиске X-сервера
  тоже не участвует — этот путь ходит по старым заметкам, сервер его не видит.
- Рабочих варианта два. Первый: файл символов и файл типов под НОВЫМИ именами
  в системном дереве `/usr/share/X11/xkb/symbols` и `/usr/share/X11/xkb/types`
  (новое имя не перезаписывается обновлениями) плюс строка раскладки в
  `autostart-x11`. Второй: полностью в userspace — сгенерировать полный keymap
  и скормить его xkbcomp с пользовательским каталогом поиска через флаг -I;
  минус — рассинхрон с RMLVO-состоянием сервера, который читает наш виджет
  раскладки через `setxkbmap -query`.
- Риск обновлений: миграции xkeyboard-config меняют каталог (на Arch 2.45
  превратил `/usr/share/X11/xkb` в симлинк на `/usr/share/xkeyboard-config-2`;
  Arch несёт 2.47-1 с февраля 2026, Manjaro тянется следом). Кастомные файлы
  в старом каталоге блокируют pacman-транзакцию — лечение известно: убрать
  файлы перед апгрейдом, вернуть после (Arch-форум, июнь 2025). Процедура
  редкая и задокументированная.

Проблема всего класса одна и фундаментальная: ремапер сидит НИЖЕ xkb и не
может повлиять на то, во что xkb переводит клавишу. Кириллический keysym
рождается выше — в X-сервере. Поэтому «конфиг ru → латиница под Ctrl» у
evdev-ремапера возможен только одним способом: перенести кириллицу внутрь
самого ремапера (слоями), а системную раскладку оставить латинской. Это и
есть рецепт из обсуждения 1435 канаты — он работает, но означает: раскладку
переключает kanata, а не наш `grp:alt_shift_toggle`; виджет раскладки qtile
теряет смысл; наш стек перестраивается вокруг демона.

Специфика keyd на X11, собранная по issues (проверено 2026-10-16): демон не
знает xkb-групп и keycode-мир ремапера расходится с keysym-миром сервера —
issue 26; рестарт демона эмулирует выдёргивание клавиатуры и сбивает
setxkbmap и xset — issue 183; ломались LED-индикаторы раскладки
(`grp_led:scroll`) — issue 554; кейд-слои с кириллицей ломают обычные
Ctrl-хоткеи, лекарство автора — «добавьте КАЖДЫЙ хоткей в слой» — issue 888.
Для И-55 сам по себе keyd ничего не даёт: его сила — ремапы физических
клавиш, а не латиница под модификатором.

## 9. И-55 — вердикт: чистый xkb-вариант против evdev-ремапера

Вердикт Института: на X11 надёжнее чистый xkb-вариант. Аргументы:

- Точка приложения. Проблема живёт в слое keysym: X-сервер переводит keycode
  в кириллицу, и приложение не может сматчить Ctrl+C. xkb-вариант правит
  ровно это место: латинский keysym с модификатором рождается в сервере, и
  его видят ВСЕ клиенты — qtile, Alacritty, X-core-приложения, GTK и Qt.
  evdev-ремапер до этого слоя не дотягивается физически; его «решение» —
  забрать раскладку у xkb целиком и жить в своём keycode-мире.
- Права и сущности. xkb-вариант — ноль демонов, ноль новых прав, ноль
  udev-правил: два текстовых файла и правка одной строки в autostart.
  Любой evdev-вариант — это демон с чтением всех нажатий и uinput-правом,
  то есть ровно «демон-кейлоггер», которого рамка просит избегать.
- Совместимость со стеком. xkb-вариант сохраняет `grp:alt_shift_toggle`,
  виджет раскладки, `setxkbmap` и привычную модель целиком. kanata-рецепт
  ломает всё перечисленное и требует держать раскладку в двух местах.
- Честные минусы xkb-варианта, чтобы вердикт не был рекламой: файлы лежат в
  системном дереве (нужен разовый root-шаг и регламент на мажорные
  обновления xkeyboard-config); некоторым приложениям с собственным IME
  всё равно; у сообщества есть единственная оговорка про Chromium;
  потребуются тест-матрица по приложениям и пере-применение при выдёргивании
  внешней клавиатуры (udev сбивает карту, а autostart этого не ловит).
- Смягчающий факт: значительная часть десктопа (GTK, Qt, Firefox,
  LibreOffice) уже матчит хоткеи латиницей самостоятельно — на стороне
  libxkbcommon/toolkit. Остаток боли — qtile, Alacritty и X-core-остаток.
  xkb-вариант закрывает остаток одной правкой; evdev-ремапер — только
  перестройкой всей модели.

## 10. Рекомендации: лучший плюс запасной

### И-54 — конвертер набранного текста

Лучший — PolterType. Обоснование: единственный кандидат, работающий на X11
без root, без группы `input` и без uinput (XInput2 плюс XTest) — минимальные
привилегии под нашу рамку; лицензия MIT; проект дышит (v0.37.0 от 2026-10-15,
релизы еженедельно, 643 коммита); режим manual-only с ручным хоткеем force-switch
конвертирует последнее слово ровно по слову владельца, поддержан и жест
двойного Shift, безопасный рядом с нашим alt_shift; есть конвертация выделения
(выключена по умолчанию), русский словарь, защита идентификаторов кода (важно
для разработки), per-app исключения. Оговорки Института: молодой и небольшой
проект — заложить пилот с чек-листом; апдейтер выключить в конфиге; проверить
поведение на экране блокировки; qtile отсутствует в списке измерений автора
(соседние i3 и openbox измерены — механика от WM не зависит).

Запасной — lay-x11. Обоснование: механически чистый, лёгкий (чистый Rust,
только x11rb), MIT, двойной Shift, группы зашитые 0=us/1=ru совпадают с нашими,
есть CLI-конвертер для буфера. Минусы, из-за которых он запасной, а не лучший:
не обновлялся с 2026-05-11, issues выключены, 8 звёзд — поддержка одиночная;
требует группу `input` и uinput-правило (класс кейлоггера-демона).

Не рекомендованы: easy-switcher (root-демон, спит), xswitcher (setuid-кейлоггер,
сборка с трением), puny-switcher (без daemon не живёт).

### И-55 — раскладко-независимые хоткеи

Лучший — чистый xkb-вариант (раздел 7 и вердикт раздела 9). Это не «утилита»,
а два конфигурационных файла и правка строки раскладки — но именно такой
результат и нужен: ноль демонов, ноль прав, латиница у источника keysym.

Запасной — kanata по рецепту обсуждения 1435 (класс evdev). Берём его только
если xkb-вариант упрётся в неустранимую каверзу конкретного приложения:
цена — sudo или udev-группа, перенос кириллицы в слои kanata, отказ от
`grp:alt_shift_toggle` (переключение берёт kanata), переделка виджета
раскладки. xremap и keyd для И-55 не рекомендую вовсе: первый не решает
keysym-матчинг (его ремапы хороши сами по себе, но наша задача не про них),
второй наследует весь набор X11-проблем, описанный в разделе 8.

Точечные бесплатные костыли (существуют уже сегодня, без новых сущностей):
биндинги qtile по численному keycode вместо букв (нативная фича, описание в
доках qtile «Keys»; не работает с EzKey); дубль-биндинги Alacritty с
кириллическими keysym (рецепт из issue 7688 — пара строк в конфиге).
Дублирование кириллицей биндингов внутри config.py самого qtile НЕ советую:
issue 4162 — класс коллизий имён keysym (нижний регистр ломает заглавные
Cyrillic_ZE и другие).

## 11. Внедрение: stow-пакеты, юниты, объём работ

### И-54, PolterType (лучший)

Stow-пакет `poltertype` в dotfiles: бинарник AppImage в `~/.local/bin`
(перезаливка версией — шаг скрипта), конфиг `.config/poltertype/config.toml`
(режим manual-only, хоткеи, апдейтер выключен, при желании исключения
приложений), маленький скрипт установки. Запуск: строка в
`qtile/.config/qtile/autostart-x11` рядом с остальными аплетами — так же,
как сегодня стартует nm-applet и copyq. Systemd user unit здесь НЕ лучший
путь: под startx плюс Qtile никто не поднимает graphical-session.target,
юнит пришлось бы кормить DISPLAY вручную и дублировать логику — выбираем
существующий паттерн autostart-x11, он проверенный. Объём: 3 шага (бинарь,
конфиг, строка автозапуска) плюс тест-матрица; по часам — примерно 2—4,
большая часть — тесты по приложениям и экрану блокировки.

### И-55, xkb-вариант (лучший)

Stow-пакет `xkb-ruhotkeys`: два файла раскладки (символы и типы под новыми
именами), скрипт установки, копирующий их в `/usr/share/X11/xkb/` с новым
именем (один разовый sudo-шаг), и правка существующей строки setxkbmap в
`autostart-x11` на раскладку `us,myru` (variant-имя свободное). Альтернатива
без root — пайплайн xkbcomp с пользовательским каталогом -I, но он рассинхронит
виджет раскладки; в основную рекомендацию её не включаем. Объём: 4—5 шагов
(написать тип и вариант, скрипт-инстоллер, правка строки, тест-матрица,
регламент обновления xkeyboard-config); по часам — примерно 4—8. Тест-матрица
обязательна: qtile Super-биндинги в русской группе, Ctrl+C/V в Alacritty,
Firefox, Chromium (заявленная каверза), rofi, nvim, повтор при выдёргивании
внешней клавиатуры.

### Риски установки на Manjaro (свод по обеим категориям)

- Группа `input`: любая (easy-switcher, lay-x11, xremap, kanata) даёт
  пользователю право читать ВСЕ нажатия системы. PolterType на X11 и
  xkb-вариант права не требуют вовсе — для нас это решающий довод.
- uinput: udev-правило на `/dev/uinput` — только для запасных путей.
- `grp:alt_shift_toggle`: жесты конвертера на Alt+Shift конфликтуют с
  переключением раскладки; выбранная механика (двойной Shift) свободна от
  конфликта. Сам дефект «alt_shift ломает хоткеи с Alt+Shift» уже в стеке.
- Мажорные обновления xkeyboard-config: процедурная веха для xkb-варианта
  (см. раздел 7), редкая и задокументированная.
- Lock-screen: инъекции клавиш evdev/XTest идут И в заблокированный экран
  (документация xremap предупреждает об этом прямо). Проверка поведения
  force-switch на экране lock.sh — обязательный пункт пилота.

## 12. Конфликты с существующим стеком

- `autostart-x11` (строка 35, setxkbmap): для И-55 строка меняет аргументы
  на наш вариант; для И-54 добавляется одна строка запуска. Порядок старта
  некритичен: PolterType поднимается после иксов, на группу смотрит сам.
- `xss-lock` и `lock.sh`: прямого конфликта нет — скринлок не держит хоткеев
  и не конкурирует за группу. Косвенные два: инъекции конвертера проходят на
  заблокированный экран (см. риски выше) — в пилоте проверить, что force-switch
  на lock-screen не портит поле пароля; у PolterType есть пауза через хоткей —
  на время блокировки гасить не обязательно, если ручной режим.
- Виджет раскладки (`widgets.py`, опрос `setxkbmap -query`): xkb-вариант
  полностью совместим (RMLVO-имена сохраняются); kanata-запасной ломает виджет —
  ещё один аргумент держать его запасным.
- copyq (менеджер буфера): PolterType при конвертации выделения сохраняет
  буфер сам, но copyq запишет транзитное содержимое в историю — при желании
  добавить исключение в copyq или просто знать.
- flameshot и dunst: не пересекаются с раскладкой — точек конфликта не найдено.
- Qtile-биндинги: пока xkb-вариант не внедрён, Super-хоткеи при русской группе
  мертвы (раздел 3) — внедрение их оживляет; отдельных действий в config.py
  не требуется.
