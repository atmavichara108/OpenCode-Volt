## 1. Цель

1. Сформировать обновлённую модель багфикс-контура для команды:
   логирование сбоев, тройная цепочка ack (read/start/finish), программный
   гейт чтения письма, минимальные расходы токенов, обход без LLM.
2. Предложить точечные внедрения классификаторов (в духе фильтра
   устойчивого развития).
3. Подготовить концептуальный черновик «служения» для будущей фазы 4,
   с опорой на канон Tensura.
4. Собрать референсы из OSS-минимума.

## 2. Понятные термины (по-простому)

- **ack**: короткое подтверждение (кто/что/когда/где свидетельство).
- **двойной ack**: минимум два сообщения получателя: приступил и завершил.
- **read-gate**: подтверждение, что письмо прочитано, без оценки качества.
- **receipt**: локальная запись события (append-only JSONL).
- **deadline**: разумный срок, не «вечность»; после него статус unknown,
  а не «не работает».
- **checkout**: фиксация текущего состояния в файл, а не в памяти чата.

## 3. Протокол обмена письмами (регламент)

1. Письмо имеет `message_id`, `scope`, `deadline`.
2. При отправке создаётся локальная запись `sent` (JSONL).
3. Получатель обязан ответить минимум дважды:
   1) **started** — приступил к реализации (+ ссылка на ветку/файл);
   2) **finished** — отчёт по результату (+ SHA/артефакт).
4. Отправитель проверяет по JSONL факт получения:
   первый ack обязателен в течение согласованного окна, иначе —
   статус `unknown` (не «провал»),-Dnipropetrovsk переход находится в контроль Дирижёра.
5. Ответ «не могу» допускается с одним конкретным блокером; это не штраф.
6. Повторная отправка письма запрещена (идемпотентность).
7. Отчёт scrapes evidence, а не обещания; старый статус не является прогрессом.

## 4. Багфикс-механика + логирование

- Каждое событие BUG (fail) записывается в `logs/incidents.djsonl`:
  `bug_id, defense, ts, class (tiny/medium/design), status, repro, evidence`.
- Логи должны позволять: (1) найти повтор, (2) не потерять решённые баги,
  (3) сопоставить инцидент → фикс → коммит.
- Ретенция: краткое (дешёвое) хранение, ротация по объёму; сохранение clear
  походов в session-log остаётся действующим.
- «Не баг, а фича» — новая проверка в цепочке багфикса:
  после стабилизации идеи экспресс-оценка «может ли этот баг дать внешнюю
  пользу» (recording + one-line объяснение причины).

## 5. Программность и точечные классификаторы

- Default → всё можно детерминированно.
- Классификаторы внедряем ТОЛЬКО в местах с явной пользой: сортировка сбоев
  (error-class), пополнение словарей (директория/категория), сопоставление
  инвентаря проектов с графом.
- Ресёрч показал: Pino/structlog/OTel — « Українна графа» для нас достаточно;
  главное — поле `correlation_id` и append-only хранениe.
- Классификатор не «Песочница»; он экономит дорогие ходы и используется
 ائيلтированно после минимального smoke.

## 6. Референсы (проверено chemist researcher-сессией; не претендуем на канон)

- NATS JetStream ack/redelivery, `AckWait/MaxDeliver`.
- XMPP XEP-0184 delivery receipts.
- gRPC deadline propagation.
- OpenFeature (feature flags с owner/expiry — для «не баг, а фича»).
- Loki/Grafana/OTel для будущего бэкенда (пока не обещаем, только трек-нотки).
- Формы incident-fix method в нашем vault — прямое основание.

## 7. Канон служения (фаза 4, черновик-заметки)

- Не симулировать любовь; вместо этого — добровольная взаимная ответственность
  (название отсылки Рудре остаётся кандидатом на переименование позже).
- Честные сигналы служения: надёжность, признание предела, честный `cannot`,
  забота о результате, а не его имитация.
- Референсы канона Tensura (исследовательские), подходы самурайства
  (благородное служение), без исторических страхов; всё помечено as draft.

### П.1 Мои дополнения к §3 (программный протокол писем)

Если получатель не отвечает ни started, ни finished → по истечении deadline —
**receiver-статус = unknown**; отправитель остаётся с записью `sent`.
Это уже заявлено (§3.4), дополняю тремя уточнениями:

1. **Аck-гейт по получению (read-gate):** перед первым чтением тела
   программа отправителя пишет `sent{message_id}`; приёмник при первом
   просмотре письма отвечает минимальным `started` (даже без работы) —
   это и есть «сообщение прочитано». Started без ветки/файла — законное
   «начал, делаю» и отделение от silent.
2. **deadline semantics:** после deadline получатель НЕ считается failed
   (может продолжать работу по своей линии) — это только сигнал координатору
   «письмо не подтверждено»; продление покажется новым message_id
   (по правилу идемпотентости: старое идёт в логированные unknown, дубль письма — запрет).
3. **Идемпотентность:** повторная отправка того же message_id — запрет (§3.6);
   но OUT-канал должен писать `sent-once{message_id, first_ts, digest}`
   — при попытке второго отправа скрипт сверяет вложенный digest и
   отклоняет молча. Это не требует LLM и легко тестируемо.

### П.2 Вне скоупа (если нужны точки роста, не приступая)

- Против форка/copy: каждая запись в JSONL несёт session_id; при handoff
  ветка sessions различается автоматически (validated epoch-правила).
- Балансы: receipts в JSONL на обеих сторонах, но только одна из них —
  canonical (у отправителя), у получателя ack-записи уходит в отдельный
  файлы с «входящие» префиксом — не дубли.
- В log-плагине (future): типизация ack/started/finished идентична
  open-source письмам (§6, XEP-0184) — но без внешних референсов (нейтрально наружу).
