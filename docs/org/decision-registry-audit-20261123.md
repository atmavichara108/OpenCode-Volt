# Сверка двух реестров решений и прослеживаемость канона — 23.11.2026

Задача хода: каждый канон моего слоя (`docs/org/`: реестр имён, реестр манифестов) должен
вести к записи слова владельца **в реестре решений**, и ни одно решение не должно висеть
без адреса. Канон «письмо ≠ память» работает только если адрес есть.

Метод: прочитаны оба реестра целиком; id собраны регуляркой и сопоставлены; для каждой
строки реестра имён и реестра манифестов проверено, есть ли id решения-источника; по
рекрутинговому контуру — история спеки через `git log`/`git show`; по слово владельца —
цитаты в `01-Policies/decisions-registry.md` (`basis: quoted`) и в
`~/Projects/recruiting-hr/docs/canon/roles.md`.

### Н-15. В моём реестре решений не было ни одной ссылка-строки на решения `Р-*` — при 18 канонах, которые на них держатся

Мои два реестра ссылаются на **18 решений** второго реестра: 15 — в реестре имён
(Р-004, Р-007, Р-014, Р-015, Р-026, Р-029, Р-034, Р-046, Р-050, Р-064, Р-071, Р-078,
Р-080, Р-097, Р-113) и 9 — в реестре манифестов (Р-005, Р-014, Р-034, Р-043, Р-064,
Р-071, Р-097, Р-113, Р-118); объединение — 18. Все 18 существуют в
`01-Policies/decisions-registry.md` (расхождений по существу нет). Но в
`docs/org/decision-registry.md` **не было ни одной строки-ссылки** на `Р-*` — только
описание слоёв в шапке. По Р-048 такие решения должны иметь ссылка-строку **в обоих**
реестрах.

**Правка (мой слой):** в `docs/org/decision-registry.md` добавлен раздел «Перекрёстные
решения (ссылка-строки по Р-048)» — 18 строк-указателей (id · дата · что даёт · где
используется в слое `docs/org/`), **без дубля содержания**: полный текст решения остаётся
в каноническом месте — в `01-Policies/decisions-registry.md`.

### Н-17. «Outrich-office» — это вывод УАС по образцу, а не дословное имя владельца

По диску: Р-Д-009 (30.10) задаёт образец офисной модели — «Офис Серплюкс - serp-office +
добавить агента для разработки … - senior-dev»; Р-Д-011 (30.10) — «Аутрич Цеху - Senior-dev».
Дословного имени для **офиса** линии Аутрич владелец не называл: «Outrich-office» — это
применение канона Р-Д-009 («офис = `<имя>-office`») к линии Аутрич, то есть **вывод УАС**.

**Почему это важно:** вопрос владельцу «подтверди имя Outrich-office» был поставлен неверно
— слово владельца его не давало. Правильная постановка: либо владелец называет офис Аутрича,
либо остаётся вывод УАС с пометкой. Это же снимает часть путаницы с коллизией `Senior-dev`
(Н-13): канон Аутрич·Цеха — слово владельца (Р-Д-011), а «Outrich-office» — мой вывод.

### Н-18. Рекрутинговые линии названы — не хватает только имени агента-носителя проекта

Реестр имён утверждал, что у трёх линий рекрутинга «канонического имени нет — слово
владельца». По диску это неточно:

- **Р-078** (04.11, `basis: quoted`) — агентство включено в экосистему, названы и адресованы
  две линии: «Смотритель HR» (`ses_f0861c5…`) и «Офис» (`ses_ef334a11…`);
- **Р-080** (04.11, `basis: quoted`) — слово владельца исправляет роли: «поиск целиком на
  Офисе — он и сканит, и пишет в личку, и ведёт воронку»; Смотритель HR — «глаза» проекта;
  учёта/оформления/документов/календаря в проекте нет;
- **третья линия** «Отдел Разработки HR» (`ses_e57fd2b2…`) — §2 спеки
  `docs/specs/recruiting-agency.md` (роли и адрес) и `~/Projects/recruiting-hr/docs/canon/roles.md`.
  **Уточнение:** слово владельца (Р-080) описывало две линии; наименование и зону третьей
  ввёл ЦУ в спеку (коммит `b9c36ba4`, 04.11) — слово владельца «Отдел Разработки HR» не
  даёт.

Итого: **линии названы; не хватает только имени агента-носителя проекта** — primary
`top-manager.md` («Дежурный менеджер кейса») — самоописание проекта, не канон, и его имя
файла совпадает с глобальным `Top-manager` (Н-11). Вопрос владельцу сужается с «три имени
линий» до «имя primary рекрутингового проекта» (или решение оставить выводом проекта).
