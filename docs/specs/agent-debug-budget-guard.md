# Agent Debug Budget Guard

## Проблема (выявлена 2026-09-25)

На диагностике focus2-бага Pip-Boy агент потратил ~40+ ходов, 20+ повторных
чтений `Workspace.js`, многократные добавления/удаления `console.log` и повторные
Playwright-прогоны. Итог достижим был за ~1/3 бюджета. Причины:

1. Нет лимита на диагностические шаги — агент ушёл в бесконечную спираль.
2. Повторные чтения одного файла из-за компакции окна вместо точечного grep.
3. Пошаговые микро-правки вместо одного решительного исправления.
4. Интроспекция DOM из page-context недоступна — попытки отлаживать через
   консоль, которая не даёт доступа к внутреннему состоянию объекта.

Цель спеки: **программно** ограничивать диагностические циклы и подсказывать
правильный путь, чтобы агент не тратил бюджет впустую.

## Жёсткий лимит: диагностика = максимум 4 шага

При расследовании неисправности агент обязан соблюдать бюджет:

```
Step 1  Прочитать РОВНО ОДИН символ/функцию через read(symbol=...) или grep
        (НЕ перечитывать файл целиком). Сформулировать 1 гипотезу.
Step 2  Один проверочный прогон (тест/команда). Подтвердить/опровергнуть.
Step 3  Если гипотеза верна — сразу решительный фикс (одно цельное изменение).
        Если нет — выдвинуть следующую гипотезу.
Step 4  Если причина НЕ найдена за 4 шага — СТОП. Зафиксировать как известную
        проблему, оставить код чистым, передать человеку/иной сессии.
```

Правило: **никогда** не выполнять один и тот же диагностический прогон более
двух раз подряд с одинаковым ожиданием. Если результат повторяется — это
новый факт, а не повод ещё раз.

## Повторные чтения: анти-паттерн

- Один файл читать целиком **не более 2 раз** за сессию на одну задачу.
- Для доступа к конкретному методу/символу использовать `read(symbol=...)`
  или `grep`, а не перечитывать весь файл.
- После компакции окна НЕ перечитывать потерянное — сразу `grep` нужный
  идентификатор.
- Файл, который уже читался в этой сессии, читать повторно только если
  менялся на диске (иначе это повтор, не новая информация).

## Диагностические console.log: добавлять максимум 2 раза

- Допустимо добавить **не более 2** временных console.log за всю диагностику.
- Каждый добавленный log обязан иметь проверочный прогон с чёткой гипотезой.
- После подтверждения гипотезы ВСЕ временные log **удаляются** до коммита.
- Нельзя накапливать логи от разных попыток в одном файле.

## Когда добавить console.log, а когда отказаться

Добавлять log только если он подтверждает конкретную гипотезу о потоке данных.

НЕ добавлять log если:
- недоступна интроспекция (например, внутреннее состояние объекта не видно
  из page-context) — тогда log бесполезен, нужно искать другой путь;
- можно понять из кода без прогона;
- уже был log с тем же результатом.

Если интроспекция программно недоступна — вместо ещё одного цикла выбрать:
- делегировать проверку отдельному агенту/тесту;
- передать проблему человеку;
- зафиксировать как известное ограничение и перейти к задаче.

## Одно решительное исправление вместо пошаговых микро-правок

- Целевой фикс: одно цельное изменение, заменяющее хрупкую логику.
- НЕ накапливать по 5–10 связанных мелких правок, каждая из которых
  требует перезапуска и прогона.
- Промежуточная правка допустима только если даёт немедленную, измеримую
  проверку на ЭТОМ шаге.

## Дорожная карта программной автоматизации

Чтобы это стало программным, а не только поведенческим правилом, реализовать:

1. **Read-guard (предлагается)** — эвристика в инструменте чтения: если
   агент читает файл, который уже читал в сессии и не менялся на диске,
   возвращать предупреждение «повторное чтение без изменений» + подсказку
   использовать grep/symbol.
2. **Diagnostic-budget counter (предлагается)** — счётчик числа
   read/grep/eval-прогонов в рамках одной задачи; по достижении лимита
   напоминать о передаче проблемы.
3. **Console.log hygiene check (предлагается)** — pre-commit gate, который
   не пропускает временные `console.log` с маркером-префиксом
   (например, `[dbg]`) в production-файлах.

## Acceptance

- Агент завершает типовую диагностику неисправности за ≤4 диагностических
  шага и ≤2 полных чтений файла.
- Временные console.log не попадают в коммиты (проверяется).
- Задачи с недоступной интроспекцией решаются делегированием/передачей,
  а не повтором циклов.
- Регрессия: focus2-тип бага (клик-по-заголовку) не должен занимать >4 шагов.
