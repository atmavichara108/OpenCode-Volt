# Центр стратегического планирования и менеджмента (ЦСПиМ)

## 0. Слово владельца (basis: quoted, 2026-10-30)

«кстати я вспомнил что хотел создать центр стратегического планирования и
менеджмента (ЦСПиМ) - в его ведомстве все роадмепы, таски, инбоксы, квесты и
всё в этом дуке всей экосистемы корабля. то есть по факту от планирования до
менеджмента по всем квестам. нужн отчаственно продумать его функционирование,
взаимосвязь с другими ведомствами и спроектировать своего агента. ты уже знаешь
как всё организовать при участии ипт, хпф, да и всех остальных кого требуется
задействовать для этого.»

Статус документа: **proposed — проектирование**. До approval владельца спека
не канон; сессия, агентный файл и манифест не создаются.

## 1. Назначение

ЦСПиМ — орган Корабля, который отвечает на вопросы **«что делаем, зачем, в
каком порядке и когда результат»** по всей экосистеме: роадмапы, таски,
квесты, инбоксы-очереди. Проще говоря: от планирования до менеджмента по всем
квестам (слово владельца).

## 2. Модель: план / исполнение / координация / смысл — четыре разных вещи

Ключевое проектное решение: разделить функции, которые сегодня смешаны.

| Вещь | Кто владелец сегодня | Что означает |
|---|---|---|
| **Смысл** («зачем») | ХПФ | доктрина, цели захода, концепты |
| **План** («что и в каком порядке») | *нет единого владельца* | роадмапы, таски, квесты живут разрозненно |
| **Исполнение** | ведомства / primary-агенты | работа, код, приёмки |
| **Координация** («кто кем и через что») | ЦУ | маршруты, решения, почта, канон-реестр |

**ЦСПиМ — владелец плана.** Не смысла (ХПФ), не исполнения (ведомства), не
координации (ЦУ). Это заполняет дыру «плана без хозяина», не забирая чужих зон.

Вердикт Храма (мандат csipm-design-hpf, 10-30): ЦСПиМ — **живая проекция +
сторож дрейфа**, не дубль-реестр (дублирование — наш системный дефект, ADR-029).
Образец — Ротатор: каталог-SSOT + health; для ЦСПиМ — план-SSOT +
приоритет-health. При конфликте «план vs смысл» — гейт Храма (что изменилось:
смысл устарел или план дефектен), финальный владелец — владелец Корабля.

## 3. Зоны (что принимает на баланс) — черновик, уточняется по инвентаризации ИЦ

Классы артефактов планирования экосистемы:

1. **Роадмапы** — проектов (`docs/specs/*roadmap*`) и ведомств; единый свод
   порядка.
2. **Таски** — `TASKS.md` (волт), проектные task-реестры.
3. **Квесты** — `11-Quests/quests.md` (Q-xxx): постановка → исполнение → done.
4. **Очереди/инбоксы планирования** — `10-Deck`, decision-queue, waits
   (осознанные ожидания).
5. **Цели** — `~/.local/state/opencode/goal.json` (Р-039): реестр активных
   целей/KPI контуров.
6. **Техдолг и память планирования** — `04-Memory/tech-debt*`.

Модель владения (SSOT-правило): **содержание остаётся у исполнителя, порядок и
приоритет — у ЦСПиМ.** ЦСПиМ не переписывает роадмап ИПТ, но отвечает за
сводный порядок и межведомственные приоритеты; расхождение — сигнал, не молчание.

### 3.1 SSOT-карта planning-слоя (инвентаризация ИЦ, мандат csipm-design-inventory)

14 артефактов по классам: ПЛАН — TASKS.md, 11-Quests/quests.md, 10-Deck
(+_gen/quests_data.py), роадмапы проектов (AndroidOS, ability-lab, dv-hub,
serp), docs/specs/*; ПАМЯТЬ — tech-debt, active-context, facts, ship-versions;
ОЧЕРЕДЬ — goal.json, waits.jsonl, decision-queue (8360 карт без TTL и
наследника); ВХОД — .opencode/memory/inbox.md каждого ведомства; РЕШЕНИЯ —
два реестра (dotfiles decisions.md и волт 01-Policies/decisions-registry.md).

Находки, которые ЦСПиМ обязан закрыть по построению:
1. План и исполнение не связаны: TASKS/квесты/Deck не указывают на
   goal.json/waits; связка «пункт плана ↔ цель/ожидание» ручная → невоспроизводима.
2. Дубли: TASKS vs quests vs Deck/_gen (три экземпляра задач); два реестра решений.
3. Устаревание без сигнала: TASKS 11 дней, active-context 5 дней — нет свежести
   в статусных выводах.
4. Очередь без наследника: decision-queue растит без TTL/владельца.
5. Свода роадмепа нет: сколько роадмепов и в каком состоянии — не видно никому.

## 4. Границы (anti-goals)

- Не исполняет код и не становится primary ни одного проекта/ведомства.
- Не канонизирует: канон — слово владельца через ЦУ (Р-записи).
- Не подменяет ЦУ: ЦУ остаётся оперативным координатором (маршруты, peer-registry,
  почта, решения); ЦСПиМ — planning-слой. Пересечение — предмет ревью обеих сторон.
- Не трогает агентский контур (УАС) и память смыслов (ХПФ).
- Метрика Р-024: центр планирования обязан снимать вопросы владельца; центр,
  который планирует ради плана, — декорация (тест «декорация/нет»).

## 5. Функционирование (черновик контура)

1. **Приём постановки** — слово владельца/ведомства → квест или таск в реестре.
2. **Планирование** — декомпозиция, порядок, зависимости, WIP≤1 на исполнителя
   (по Р-039-дисциплине).
3. **Менеджмент** — ведение до результата: статусы, приоритеты, дедлайны/слоты,
   эскалация при простое (TTL: просроченная задача — дефект, не тишина).
4. **Сверка** — свод «план vs факт» по порогу (не по каждому чиху): отклонение
   озвучивается, не прячется.
5. **Отчёт владельцу** — human language (А5): что в плане, что сдвинулось,
   что ждёт его слова.

## 6. Агент ЦСПиМ (проект — зона УАС, материал — имя от владельца)

Досье УАС: docs/org/drafts/csipm-agent-design.md (роль, границы, manifest-форма
11+4, mandate-source — слово владельца 10-30 дословно). Ключевое из досье: агент
читает planning-реестры read-first, ведёт канву, контролирует WIP=1, конфликты
приоритетов — на арбитраж ЦУ/владельца.

Профиль (до проекта УАС — черновик ЦУ):

- **Класс:** planning-primary своей сессии; читает все planning-реестры
  (TASKS, квесты, роадмапы, goal.json, waits), ведёт почту,Goal.
- **Пишет:** только свою зону (spec-home, planning-реестры ЦСПиМ, отчёты);
  в чужие репозитории — через их primary.
- **Не:** код приложений, канон (кроме фиксации слова владельца через ЦУ),
  агентский контур, молчаливое пересечение чужих зон.
- **Режим:** /goal (Р-039) перед ходом ≥1; WIP один.
- **Имя:** кандидаты УАС — **Strateg** (рекомендован), Wayfinder, Planner;
  окончательное имя — решение владельца (реестр Р-Д-009, через Ворота).

## 7. Взаимосвязи с ведомствами (карта на проектирование)

| Ведомство | Связь с ЦСПиМ |
|---|---|
| ЦУ | оперативная координация + канон-реестр; ЦСПиМ предлагает план/приоритеты, ЦУ маршрутизирует и фиксирует решения |
| ИЦ | куратор planning-контура (по образцу Р-038?) — на решение владельца; инвентаризация артефактов (мандат csipm-design-inventory) |
| ИПТ | методики планирования, приёмка методов; роадмап ИПТ на балансе ЦСПиМ по порядку |
| ХПФ | смысл целей; тест «декорации» для плана (мандат csipm-design-hpf) |
| УАС | агент + манифест ЦСПиМ (мандат csipm-design-uas) |
| Абилити Лаба | приёмка контура менеджмента (метрики: процент целей закрытых по criteria) |
| Отделы Приложений/Движков | их работы встают в сводный план как задачи/квесты |

## 8. Процесс учреждения (по образцу a/b/c)

1. Проектирование: спека (этот документ) + ответы ИЦ/ХПФ/УАС.
2. Approval владельца (слово: организуем/апрув).
3. Р-запись (реестр решений).
4. Манифест `docs/org/csipm.md` — УАС (11+4 поля, mandate-source — слово 10-30).
5. Сессия-носитель (создаёт ЦУ по слову владельца) + имя агента (слово владельца).
6. Карточка `03-Projects/csipm.md`, строка peer-registry.
