# P-3. Архитектура рубки

## Словарь (один на всех: досье, Пип-Бой, протоколы)

- **Прибор** — тайл/модуль рубки: читает один источник, показывает одно
  видение состояния. Может нести органы управления (см. ниже).
- **Отсек** — группировка приборов по смыслу (Мост, Машинное, Почта,
  Аварийный). Отсек не хранит данных — только раскладка.
- **Орган управления** — элемент прибора, который **действует** (кнопка,
  поле ввода). Не имеет собственных прав: путь действия — всегда через
  Ворота владельца или письменно (см. §3).
- **Рубка-контроллер** — единственный компонент, которому разрешено
  вносить изменения (паттерн из досье, часть 1). Приборы и органы
  управления — только читают/просят.

## §1. Владение данными (железное правило)

1. Источник правды каждого прибора — **реестры, диск или открытый API
   Корабля**. Рубка данных не хранит: ни кэша дольше сессии рендера,
   ни своих копий состояний.
2. Прибор потерял источник → показывает «нет данных», серым, с меткой
   времени последнего чтения. **Не выдумывать**, не заполнять последним
   известным без пометки.
3. Всё, что лежит в Deck/проекциях, — `ssot: false` (канон волта);
   рубка не делает исключений.

## §2. Маппинг прибор → источник (этап A, 7 приборов из досье)

| Прибор | Источник | Режим |
|---|---|---|
| Состояние корабля | opencode serve (сессии, статусы, провайдеры, инструменты) | чтение API |
| Ведомства (живые сессии) | opencode serve: список сессий + peer-registry | чтение API |
| Квесты | `11-Quests/` реестр ЦУ + `Q-*.md` | чтение диска |
| Аварии (инциденты) | `~/.local/state/opencode/incidents/` + журналы гомеостаза + **журнал Ворот + session-cop report** (расхождения реестра — тоже инциденты; правка ИЦ) | чтение диска |
| Решения на апрув | decision-queue (control-plane) + events.json Ворот | чтение диска |
| Ротатор моделей | реестр Р-023 + факты подключений | чтение диска/API |
| Почта | `~/.local/share/ship-mail/inbox/<sid>/` (файлы = истина) | чтение диска |

Чего на этапе A **нет** (честно, из досье): здоровье моделей как лимиты
(нет телеметрии), расход денег, единый список сессий разных серверов.
Эти приборы не рисуем, пока не появится источник.

## §3. Органы управления → путь действия

Кнопка никогда не пишет сама. Разрешённые пути, по возрастанию веса:

1. **Кнопка-просьба** → открывает форму owner-gate (`ask_confirm`,
   `ask_choice`) — владелец жмёт да/нет, форма есть канон.
2. **Кнопка-письмо** → готовит письмо и вызывает `ship-mail.sh send`
   (пример: ответ ведомству, запрос статуса).
3. **Кнопка-команда** → только через Рубка-контроллер, только действия
   из белого списка. **Двухключевое правило (правка ИЦ):** белый список =
   что технически можно; Ворота = что разрешено сегодня. abort/fork
   чужой сессии — только через Ворота (`ask_confirm`), поверх белого
   списка. Урок: изменение состояния без доказательства и без слова
   владельца = ложь.
4. **Журнал действий (правка ИЦ):** Рубка-контроллер пишет ВСЕ действия
   в журнал lineage — действие всегда оставляет след (кто, что, когда,
   по какому разрешению).

Прямых путей «кнопка → запись в реестр/диск/DB» не существует.

## §4. Правила контура

- Чтение — свободное; изменение — только Рубка-контроллер (досье, ч.1).
- Новых источников в приборах нет без записи в §2 (правка P-3 — через
  фиксацию ЦУ, не молча).
- Каждый прибор можно выключить индивидуально (kill-switch модуля
  Пип-Боя) — авария прибора не роняет рубку.
- Авто-живость (условие этапа A): конвейер обновления — по событиям
  SSE-потока, fallback-опрос по таймеру; на экране всегда метка
  «данные на <время>».

## §5. Расширение (волны B/C)

Новый прибор = новый модуль по шаблону Пип-Боя v11 (архитектура модулей
и событий уже есть) + строка в §2 + приёмка по P-4. Отсеки и раскладки
меняются конфигом, не кодом. Переход A→B→C не переделывает ядро
(канон досье: C растёт из A/B эволюционно).
