## Ограничения

- Не менять app code или tests.
- Не трогать pre-existing изменения, включая существующие локальные документы.
- Не удалять и не передвигать `v1.0.0` по умолчанию, даже если remote не найден.
- Не переписывать публичную историю.
- Коммит, tag и push разрешены только после отдельных явных approvals,
  описанных ниже.
- Если canonical Vault недоступен, остановиться с `BLOCKED`; локальный fallback
  не использовать.

## Обязательный порядок выполнения

### 1. Зафиксировать исходное состояние

В `/home/rudra/Projects/serp` сначала прочитать применимые локальные
`AGENTS.md` и `README.md`, затем без изменений выполнить и сохранить вывод:

```bash
git status
git branch --show-current
git rev-parse HEAD
git show --no-ext-diff --stat --oneline bdc9a54
git show --no-ext-diff --stat --oneline 3f80fcc
```

Проверить, что это нужный репозиторий и текущая ветка `main`. Сверить
`HEAD` с intended baseline `bdc9a54`. Несовпадение не исправлять автоматически:
зафиксировать его и запросить решение.

### 2. Проверить локальное и remote state тега

Ничего не менять на этом шаге. Проверить, что именно разрешается именем
`v1.0.0`, является ли объект annotated tag или иным объектом, и существует ли
remote-ссылка:

```bash
git tag -l v1.0.0 -n99
git show-ref --tags --dereference -- v1.0.0
git rev-parse v1.0.0^{commit}
git cat-file -t v1.0.0
git cat-file -p v1.0.0
git remote -v
git ls-remote --tags --refs <remote> v1.0.0
```

Вместо `<remote>` использовать фактически настроенный remote и явно записать,
если remote отсутствует, недоступен или тег не найден. Если тег опубликован
или присутствует на remote, сохранить его неизменным.

### 3. Проверить границы документального закрытия

Проверить diff и перечень затронутых файлов относительно исходного состояния.
Убедиться, что изменения закрытия v1.0 ограничены разрешёнными документами,
а app code и tests не изменялись. Не включать в работу pre-existing изменения и
локальный pointer. При обнаружении неразрешённого файла остановиться и
запросить решение, не исправляя его автоматически.

`CHANGELOG.md` не менять автоматически, если это создаёт несоответствие между
уже документированным `[1.0.0]` и выбранной схемой. При таком несоответствии
остановиться и запросить решение пользователя.

### 4. Сохранить legacy tag

Старый `v1.0.0`, если он опубликован или найден на remote, оставить как есть.
Даже если remote не найден, по умолчанию не удалять и не передвигать тег.
Перенос допускается только по варианту B ниже, после доказательства
`private/unpublished` состояния и отдельного explicit approval.

### 5. Запросить отдельные решения до действий

До создания коммита запросить отдельное явное решение пользователя на коммит
документационного закрытия v1.0. До создания тега запросить отдельное явное
решение на annotated patch tag. Push требует третьего отдельного explicit
approval. Точное имя и момент нового тега пользователь выбирает после проверки
состояния; рекомендация `v1.0.1` не является автоматическим разрешением.

Рекомендуемый non-destructive вариант: сохранить legacy `v1.0.0`, закоммитить
closure docs, затем создать `v1.0.1` на новом коммите.

### 6. Подготовить и проверить commit target

После approval выполнить только согласованный документационный commit. Перед
tag проверить чистоту и target:

```bash
git status --short
git diff --check
git rev-parse HEAD
```

Не тегировать dirty, неодобренное или неидентифицированное состояние. SHA
target записать в отчёте и сверить с результатом `git rev-parse` непосредственно
перед tag.

### 7. Создать tag только после отдельного approval

Если пользователь выбрал создание тега, он должен быть annotated, с явным
сообщением. Пример команды выполняется только после approval и с согласованным
именем/сообщением:

```bash
git tag -a <approved-tag> <verified-target-sha> -m "<approved message>"
```

Записать имя, сообщение и target SHA. Не использовать `git tag -f`,
`git tag -d`, force push или любые способы переписывания истории.

### 8. Push только после отдельного approval

Push не входит в approval на commit или tag. Если он отдельно разрешён,
выполнить только согласованный push и затем перепроверить remote state.

### 9. Финальная проверка

После согласованных действий проверить:

```bash
git show-ref --tags
git cat-file -t <approved-tag>
git cat-file -p <approved-tag>
git status
git log --oneline --decorate -n 10
```

Для созданного тега подтвердить annotated object, явное сообщение и ожидаемый
target SHA. Если действие не было отдельно одобрено, оно не выполняется.

## Decision Matrix

| Вариант | Действие | Условия и риски |
|---|---|---|
| A. Рекомендуемый non-destructive | Сохранить старый `v1.0.0`; актуальный baseline выпустить как `v1.0.1` на новом documentation-commit | Нужны отдельные approvals на commit и tag; legacy consumers не ломаются |
| B. Перенос `v1.0.0` | Перенести `v1.0.0` на новый target | Только при доказанном `private/unpublished` теге и explicit approval; риск для consumers, даже при ошибочной оценке публикации |
| C. Отложить tag | Не создавать новый tag до уточнения release policy | Безопасный вариант при несогласованных changelog, ownership, remote state или правилах релизов |

Точное решение по варианту, имени и моменту тега принимает пользователь после
проверки состояния. Рекомендация A не отменяет этот gate.

## Acceptance Criteria

- Проверены `AGENTS.md`, `README.md`, status, branch, `HEAD`, `bdc9a54` и
  `3f80fcc`; результаты сохранены.
- Проверены локальный и remote state `v1.0.0` без изменений на шаге проверки.
- Pre-existing изменения и local pointer не изменены.
- Подтверждено, что app code и tests не менялись.
- Legacy `v1.0.0` сохранён, если нет отдельно доказанного и одобренного

- Commit, tag и push выполнены только при соответствующих отдельных approvals.
- Любой созданный tag annotated, имеет явное сообщение и проверенный target SHA.
- Не использовались force-move/delete tag, force push или переписывание истории.
- `CHANGELOG.md` не приведён в несоответствие без отдельного решения.
- После действий успешно проверены `git show-ref --tags`, `git cat-file`,
  `git status` и `git log`.
- Наличие этого spec само по себе не засчитывается как выполнение критериев.

## Rollback / Abort Criteria

Немедленно остановиться и ничего не исправлять автоматически, если:

- canonical spec недоступен;
- репозиторий, branch или baseline не совпадают с ожидаемыми;
- обнаружены неразрешённые изменения, app code/tests или конфликт с pre-existing
  состоянием;
- невозможно достоверно определить local/remote state `v1.0.0`;
- обнаружено, что tag опубликован, когда рассматривался вариант B;
- target SHA изменился, HEAD dirty или commit/tag не получили отдельный approval;
- `CHANGELOG.md` не согласуется с выбранной схемой;
- любая финальная проверка не проходит.

При abort не удалять созданные ранее пользователем объекты, не делать reset и
не выполнять force-операции. Если согласованный commit/tag уже создан, rollback
не должен переписывать историю: остановиться, сохранить факты и запросить
отдельные инструкции пользователя. Push никогда не считать разрешённым по
умолчанию.
