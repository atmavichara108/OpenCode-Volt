# Модель калибровки ведомств

**Слово владельца (2026-10-19, basis: quoted):** «нужно разработать простую
модель такой калибровки под разные варианты создания новых ведомств и их
отделов, она будет входить в твой сверхнавык модернизации и создания
ведомств».

**Назначение:** одна и та же процедура приводит любое ведомство/отдел в
рабочее состояние экосистемы — предсказуемо, с evidence, без «калибровки по
памяти».

## Три варианта (что меняется)

| Вариант | Когда | Ключевая особенность |
|---|---|---|
| **A. Новое ведомство с нуля** | появляется новая зона ответственности | всё создаётся: репо, конвенции, память, агенты, реестры |
| **B. Новый отдел при существующем ведомстве** | расширение зоны (кафедра, мастерская, секция) | репо родителя; отдельный адрес/канал и пакет границ; строка в оргструктуре |
| **C. Портирование существующего** | ведомство работает в чужом/общем дереве (пример: Абилити лаб в dotfiles) | переезд без потерь: рабочий каталог, протоколы/кэши, история; адрес сессии сохраняется |

## Шесть шагов (единые для всех вариантов)

### 1. Repo-корень
Где физически живёт ведомство. Правило: **ведомство = свой репозиторий**
(или явно зафиксированный отсек родителя для варианта B).
- A: создать репо, описать назначение, `.gitignore`/лицензионная рамка.
- B: каталог отсека внутри репо родителя + граница «что чьё».
- C: новый репо, перенос рабочих следов; **ничего не терять**; старые следы
  помечаются как переехавшие (не дублировать «один источник»).

### 2. Конвенции (письменный пакет)
Один файл-пакет, подписанный обеими сторонами:
- границы зон: что делает / чего не делает / что не трогает;
- гейты: что требует слова владельца (внешние действия, деньги, публикации);
- WIP-норма и правило «по одному»;
- формат отчётов и приёмки;
- кто поставляет инструменты и кто принимает результат.

### 3. Канал
- строка в `04-Memory/peer-registry.md` с **полным** sessionID; from/to только из реестра;
- liveness-проверка адреса (сессия жива, отвечает);
- правила канала: модель адресата не передавать (B15), вежливая доставка
  (idle-гейт + очередь), delivery-check по журналу;
- калибровочное письмо туда-обратно с подтверждением (адрес работает).

### 4. Память
- где живёт память ведомства (репо: `docs/`, `memory/` — по конвенции проекта);
- append-only и провенанс (`basis: quoted` для слов владельца);
- что попадает в общий волт, а что остаётся локальным;
- при переезде (C) — память переносится, ссылки переориентируются.

### 5. Реестры
- строка в оргструктуре (`01-Policies/organ-structure-*`) — место, владелец, статус;
- карточка проекта (`03-Projects/<name>.md`) с `repo:` и `spec-home`;
- при необходимости — строка в реестре стыков/движков/capability;
- обновление адреса в peer-registry (если менялся рабочий каталог).

### 6. Смоук
- первый **нейтральный** мандат в новом репо (не боевая задача);
- отчёт с evidence: путь репо, коммит, письмо туда-обратно, delivery-check,
  подтверждение конвенций, обновлённые строки реестров;
- только после этого — боевые задачи.

## DoD (готовность)

Все 6 шагов закрыты evidence: путь + коммит/hash + письмо (id и delivery) +
строка реестра + подпись обеих сторон. Отсутствие любого пункта = ведомство
не откалибровано, боевые мандаты не отправляются.

## Антипаттерны

- Калибровка «по памяти» без смоука — адрес/конвенции могут быть мнимыми.
- Адрес из чата, а не из реестра (класс INC-18).
- Устные конвенции — не существует; пакет письменный и подписанный.
- Дублирование источника при переезде (старое дерево «на всякий случай»).
- Боевые задачи до смоука.

## Уровень

Модель — **сверхнавык** (состоит из навыков: создание репо, пакет конвенций,
проверка адреса, письмо, обновление реестра, смоук), входит в сверхнавык
«модернизация и создание ведомств». Терминология — [[01-Policies/skill-taxonomy]].
