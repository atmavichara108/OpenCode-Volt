# Incident-fix — протокол «сбой → багфикс на лету»

Capability id: `incident-fix`. Канон для **всех primary-агентов**: любой
обнаруженный сбой инфраструктуры (баг, дефект, поломка инструмента/канала)
немедленно отправляется на багфикс — subagent вызывается на лету, чинит и
коммитит. Primary не копит сбои «до лучших времён» и не чинит их сам руками
(граница librarian: делегирование; граница build-агента: свой код через свой
пайплайн).

## Правило

1. **Триггер:** любой сбой инструмента, канальных механизмов (peer-comms,
   API, CLI), плагинов, скриптов, конфигов агентской инфры — в том числе
   «мягкий» (команда прошла, но результат не тот).
2. **Действие:** primary формулирует инцидент (symptom → репро → гипотеза) и
   **сразу** вызывает именованного fix-исполнителя (см. Route) без отдельного
   вопроса пользователю: вызов в рамках уже подтверждённого рабочего scope —
   штатная операция. Пользователю — уведомление постфактум (одна строка).
3. **Acceptance фикса:** воспроизведённый repro → pass; маленький точечный
   коммит в `task/*`; для mutable — reviewer до verifier (канон не меняется).
4. **Логирование:** запись в session-log (symptom, root cause, фикс, коммит);
   если сбой вскрыл факт об OpenCode — строка в `facts.md`; незакрытый — `[проверить]`.
5. **Ограничение стоимости:** фикс не должен стоить дороже сбоя. Копеечный
   repro-фикс — на лету; фикс, требующий дизайн-решения, — обычная задача в
   TASKS с этого же правила (инцидент не зависает: он либо чинится сейчас,
   либо становится задачей с ID).
6. **UNROUTABLE:** если fix-исполнитель недоступен/упал по модели — повтор
   по глобальному fallback-правилу (своя модель), не более 2 повторов, затем
   STOP и рапорт. Молча не переносить на себя.

## Route

| Слой сбоя | Куда | Исполнитель |
|---|---|---|
| глобальная инфра (`~/.config/opencode/**`-канон в dotfiles) | `meta` (global) | subagent meta |
| Vault-инфра (память, методы, index, скрипты волта) | `meta` / general в vault-scope | subagent |
| инфраструктура проекта dotfiles (скрипты, юниты, обёртки) | dotfiles primary (`builder`/`bash-dev`) | peer-comms письмо или сессия |
| код прикладного проекта | **project pipeline** (build → reviewer → verifier) | проектный первичный |
| чужой харнес (M Code, ядро OpenCode) | не фиксим: workaround + запись-факт, майнинг апстрима | первичный (фиксация) |

## Протокол записи инцидента (форма)

`symptom` (что наблюдали, вывод) → `repro` (минимальная команда) →
`root cause` (или гипотеза с меткой) → `fix` (что изменено) → `evidence`
(коммит/тест) → `статус` (fixed / workaround+задача / open).

## Известные сбои peer-comms канала (накоплено, repro-канон)

Все воспроизведены 2026-10-05; детали-канон — в [[02-Methods/peer-comms]]:

1. **Heredoc + кавычки в сообщении** → `zsh: unmatched "` — письмо с
   кавычками/скобками/спецсимволами внутри shell-строк ломает команду.
   **Канон:** текст письма всегда в файл (quoted-heredoc `<<'MSG'`),
   вызов через `"$(cat файл)"`.
2. **Блокирующий вызов + timeout** → письмо доставлено, но CLI ждёт конца
   хода получателя; у отправляющей сессии истекает timeout и она теряет
   контроль. **Канон:** доставка и ответ разделять — запускать отправку в
   background либо не ждать вывода, а читать состояние/ответ через
   `GET /api/session/{id}/message` и `GET /api/session/active`. Повторная
   отправка «на всякий случай» запрещена (дубль письма = ложный сигнал).
3. **Формат message API:** части сообщения в `content[]`, не `parts[]`
   (v2.0.23; аудит-формат `parts[]` даёт ложные пустые чтения).
4. **Внешние temp-пути** (`/tmp/opencode` и т.п.) могут быть закрыты
   `external_directory` для write-инструментов — запись файла через shell
   (bash разрешён) либо внутри рабочей области.
